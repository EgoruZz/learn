# **Основные понятия и принципы**

* **Что это:** представление синтаксиса (арифметических выражений и простых языков) деревьями: абстрактное синтаксическое дерево (AST) — только суть, конкретное дерево разбора (parse tree) — все детали грамматики; построение деревьев парсерами (рекурсивный спуск, operator-precedence — Shunting Yard и Pratt, shift-reduce, LL(1), LR); обработка — обход, интерпретация, трансформации (символьное и автоматическое дифференцирование, упрощение), компиляция в байт-код; валидация (лексическая, синтаксическая, типы, безопасность)
* **Почему выделяется в отдельный класс:** синтаксис структурно дерево (вложенность конструкций), а не последовательность или множество; дерево разбора — промежуточное представление между текстом и семантикой; операции над ним — типовые алгоритмы обходов, переиспользуемые в компиляторах, интерпретаторах, калькуляторах, конфигах и шаблонах
* **Ключевые принципы:** грамматика задаёт форму дерева: контекстно-свободная грамматика (expr → term → factor) — приоритеты операторов, рекурсия — вложенность; парсер — решатель «какая продукция применима»: сверху-вниз по первому токену (LL, рекурсивный спуск) или снизу-вверх свёртками (LR, shift-reduce); абстракция — лишнее отбрасывается (скобки, разделители — в parse tree, не в AST); инвариант дерева — каждый узел корректен по своей продукции; кэш-ключ узла (оператор+дети) — hash-consing и CSE
* **Как распознать:** «разобрать выражение/строку языка» — парсер + AST (B, A); «посчитать формулу по правилам приоритетов» — Shunting Yard (B.2) или рекурсивный спуск (B.1); «преобразовать выражение (производная, упрощение)» — трансформации дерева (C.3, C.4); «проверить корректность ввода» — валидация (D); «выполнить код/выражение» — интерпретатор (C.2) или байт-код VM (C.5); «общие подвыражения» — DAG (E.1); «key = value конфиг, шаблон {{var}}» — F
* **Границы:** рекурсивный спуск и LL(1) — грамматики без левой рекурсии (LL(1) ещё и с попарно непересекающимися FIRST); LR-парсеры мощнее (практически все детерминированные КС-грамматики), но строятся по таблицам автомата (B.6 — анализ); Shift-Reduce в простой форме (B.4) корректно обрабатывает только operator-precedence; синтаксис ≠ семантика: типы и безопасность проверяются отдельно (D.3, D.4); AST хранит дерево, а не текст — приоритеты уже в форме дерева

# **A. ДЕРЕВЬЯ РАЗБОРА**

## **1. AST (Abstract Syntax Tree)**
* **Определение:** бинарное дерево выражения: лист — константа или переменная, внутренний узел — оператор с 1–2 детьми (`+`,`-`,`*`,`/`,`^`,`~` унарный минус); построение из постфиксной записи, вычисление с окружением переменных
* **Идея:** постфикс — линейная свертка дерева (операнды до оператора); построение — стек (I.C): операнд → push, оператор → pop и склейка узла; свойства узлов (приоритет `p_of`, ассоциативность) в дереве уже не нужны — форма фиксирована
* **Почему работает:** инфиксное представление однозначно восстанавливается скобками по приоритету/ассоциативности (`to_infix`: `^` — правоассоциативен, левые операторы — скобка на правого ребёнка при равном приоритете); рекурсия по структуре дерева — любая операция (eval, size, depth, формы записи) — обход
* **Сложность:** построение O(n); eval, size, depth — O(n); to_infix — O(n·высота) худшем (скобки)
* **Обобщение:** унарные и бинарные операторы — одна схема; `~` — унарная вершина с одним ребёнком; набор операторов O, приоритеты `p: O → ℕ` и ассоциативность `a: O → {L,R}` — параметры: меняется только таблица `p_of` (переиспользует I.C `op_prec`), а построение и обходы не зависят от конкретного набора
* **Реализация:** `ASTNode` (лист/оператор) + `AST` (from_postfix, eval, to_infix, to_postfix, size, depth; `p_of` — из I.C `op_prec` + `~`)
* **Связь:** постфикс и приоритеты — I.C; дерево выражений — A.4; визитор — C.1

## **2. N-арное AST (функции и операторы)**
* **Определение:** дерево с узлами трёх сортов: константа, переменная, вызов функции (произвольная арность) или бинарный оператор; функции `sin`/`cos`/`log`/`sqrt`/`abs` — из `<cmath>`
* **Идея:** расширение языка за счёт n-арных узлов: аргументы в векторе, семантика — по имени узла (диспетчеризация); счёт контекста вычисления — окружение переменных `map<string,double>`
* **Почему работает:** узел FUN несёт имя функции и список аргументов — eval рекурсивно раскрывает аргументы и применяет функцию; приоритеты отсутствуют (форма дерева уже зафиксирована построением)
* **Сложность:** eval, to_string — O(число узлов)
* **Обобщение:** печать в инфиксе — полные скобки без ума о приоритетах (простая, но верная форма); набор функций `f: ℝ → ℝ` — параметр (имя → реализация); узел FUN поддерживает любую арность k ≥ 0 — то же дерево описывает вложенные вызовы
* **Реализация:** `FunctionAST` (kind NUM/VAR/FUN/OP2, args, фабрики var/fun/op2)
* **Связь:** бинарное AST — A.1; вычисления — C.2

## **3. Parse Tree (конкретное дерево разбора)**
* **Определение:** полное дерево разбора: нетерминалы (EXPR/TERM/FACTOR) и терминалы (токены); включает все детали грамматики (скобки, операторы), которые AST отбрасывает
* **Идея:** грамматика `expr → term (('+'|'-') term)*`, `term → factor (('*'|'/') factor)*`, `factor → NUM | '(' expr ')' | '-' factor` прямо порождает дерево: каждый узел — применённая продукция
* **Почему работает:** каноническая форма — свёртка скелета нетерминалов в AST (`to_ast`): EXPR — левая свёртка детей через операторы, TERM — аналогично, FACTOR — разбор на число/скобку/унарный минус; дамп (indent) показывает структуру разбора наглядно
* **Сложность:** построение и свёртка — O(n); dump — O(узлы)
* **Обобщение:** parse tree → AST — «очистка» от синтаксического мусора (мост из B: любой парсер может строить parse tree); грамматика — параметр: число нетерминалов и продукций произвольны, узел хранит имя нетерминала — структура универсальна для любой КС-грамматики
* **Реализация:** `ParseTree` (kind NONTERM/TERM, children, dump, to_ast; Builder — рекурсивный спуск с построением дерева)
* **Связь:** рекурсивный спуск — B.1; AST — A.1

## **4. Expression Tree (дерево выражений)**
* **Определение:** специализированное AST готового выражения: построение из постфиксной записи (I.C; получение постфикса — операторные парсеры B.2/B.3), вычисление, инф/постфиксные формы, размер и глубина
* **Идея:** обёртка над A.1 с «правильными» свойствами узлов (приоритет, ассоциативность), задающими форму дерева; пользователь строит из постфикса и работает через единый интерфейс
* **Почему работает:** инкапсуляция: AST-операции (eval/to_infix/to_postfix/size/depth) доступны как методы; дерево один раз построено — читается много раз; над этим же деревом работают оптимизации (constant folding — C.4, CSE — E.1) и трансформации (дифференцирование — C.3, упрощение — C.4)
* **Сложность:** build O(n); запросы O(n)
* **Обобщение:** то же выражение из разных источников (постфикс I.C, parse tree A.3, рекурсивный спуск B.1, Pratt B.3)
* **Реализация:** `ExpressionTree` (root + методы-обёртки над `AST`)
* **Связь:** AST — A.1; постфикс — I.C; операторные парсеры — B.2/B.3

# **B. ПОСТРОЕНИЕ ДЕРЕВЬЕВ РАЗБОРА (ПАРСЕРЫ)**

> Все парсеры B работают с потоком токенов — общие вспомогательные типы `Token` и `Lexer` (текст → токены: числа, идентификаторы, операторы, скобки; неизвестный символ — токен BAD с позицией; терминальный END) определены в начале класса и подробно описаны в D.1 (Лексический анализ). Приоритеты операторов (`+,-,*,/,^`) берутся из таблицы I.C (`op_prec`), унарный `~` — приоритет выше всех. Свойства операторов (приоритет `p: O → ℕ`, ассоциативность `a: O → {L,R}`) — параметр всех парсеров этой секции.

## **1. Рекурсивный спуск (recursive descent)**
* **Определение:** парсер сверху-вниз по грамматике с приоритетами: `expr → term (('+'|'-') term)*`, `term → factor (('*'|'/') factor)*`, `factor → NUM | VAR | '(' expr ')' | '-' factor`; возвращает AST (A.1)
* **Идея:** каждой нетерминал — функция; цикл по бинарным операторам уровня — левая ассоциативность; вложенные вызовы — приоритеты; унарный минус — новая вершина `~`
* **Почему работает:** грамматика без левой рекурсии — прямые рекурсивные вызовы по токенам; токенизация (D.1) разделена от синтаксиса — парсер работает с массивом токенов и индексом
* **Сложность:** O(n); глубина рекурсии = вложенность выражения
* **Обобщение:** любая LL-грамматика без левой рекурсии: выражение с k уровнями приоритетов — частный случай (k = 3: term → factor → число); добавление операторов — правка функции уровня; обобщение на большее число уровней — каскад функций
* **Реализация:** `RecursiveDescent` (expr/term/factor/parse над `const vector<Token>&`)
* **Связь:** parse tree — A.3 (та же грамматика, +дерево); токенизация — ввод B / D.1

## **2. Операторный парсер (Shunting Yard)**
* **Определение:** инфикс → постфикс с приоритетами (переиспользуется `op_prec` из I.C), правоассоциативностью `^`, унарным минусом (`~`), скобками; операнды — числа и переменные
* **Идея:** два стека-аккумулятора: операторы ждут в стеке, пока не придёт оператор меньшего приоритета — тогда верхние выталкиваются в выход; `~` — различие по контексту (ожидается операнд)
* **Почему работает:** инвариант: в стеке операторов приоритеты не убывают; правая ассоциативность — условие выталкивания при равенстве отключено; результат — постфикс, откуда AST (A.1) строится одним проходом
* **Сложность:** O(n) на выражение
* **Обобщение:** любые приоритеты и ассоциативности (произвольные k операторов, таблица `p: O → ℕ`, `a: O → {L,R}`) — параметры; те же таблицы — у Pratt (B.3) и shift-reduce (B.4)
* **Реализация:** `ShuntingYard` (to_postfix, to_string; `right_assoc` для `^`)
* **Связь:** приоритеты `op_prec` и постфикс-оценка — I.C; AST из постфикса — A.1; Pratt — B.3; shift-reduce — B.4

## **3. Pratt-парсер (top-down operator precedence)**
* **Определение:** рекурсивный вариант операторного парсера: вместо двух стеков приоритеты управляют рекурсией (precedence climbing); строит AST напрямую (без постфикса)
* **Идея:** `parse_expr(min)`: операнд слева; пока приоритет следующего оператора ≥ min — берём оператор и рекурсивно парсим правую часть с порогом `p+1` (левая ассоциативность) или `p` (правая, `^`); унарный минус — в `parse_prim` (нет левого операнда)
* **Почему работает:** инвариант «левый операнд уже собран»: порог `min` растёт с глубиной рекурсии, поэтому оператор с меньшим приоритетом возвращается наверх; `~` — приоритет выше всех, но обрабатывается как унарный в примитиве
* **Сложность:** O(n) на выражение; глубина рекурсии = приоритетная вложенность
* **Обобщение:** та же таблица приоритетов/ассоциативности, что у Shunting Yard (B.2) — парсеры эквивалентны по языку, различаются представлением (стек против рекурсии); расширение на бинарные функции — префиксные узлы в `parse_prim`
* **Реализация:** `PrattParser` (parse_prim/parse_expr/parse; prec — из `AST::p_of`)
* **Связь:** приоритеты — B.2 (общая таблица); рекурсивный спуск — B.1; AST — A.1

## **4. Shift-Reduce парсер (стек как рабочая память — мост из I.C)**
* **Определение:** операторный снизу-вверх: числа сдвигаются в стек значений, при появлении оператора с меньшим приоритетом выполняется свёртка (reduce) старших операторов; результат — значение
* **Идея:** shift — перенос токена в стек, reduce — применение оператора к вершине стека; приоритеты управляют моментом свёртки (как в B.2, но без выходной строки — сразу вычисление)
* **Почему работает:** два стека (значения и операторы, I.C) как рабочая память; условие свёртки — `ops.back().prec >= t.prec`, а для правоассоциативного `^` — только `>` (как в B.2); скобки — точки сброса свёртки до `(`; унарный минус — как в B.2
* **Сложность:** O(n) на выражение
* **Обобщение:** свёртки в узел дерева (а не в значение) — строит AST; полноценный LR — таблицы действий/переходов (B.6)
* **Реализация:** `ShiftReduceParser` (apply, parse; вектор-стеки значений и операторов)
* **Связь:** стеки — I.C; Shunting Yard — B.2; LR-парсеры — B.6

## **5. LL(1)-парсер (предсказывающий)**
* **Определение:** табличный разбор сверху-вниз по грамматике `E → T E'`, `E' → '+' T E' | ε`, `T → F T'`, `T' → '*' F T' | ε`, `F → num | '(' E ')'`; выбор продукции — по одному токену (lookahead), множества FIRST/FOLLOW фиксируют таблицу
* **Идея:** стек нетерминалов: на вершине нетерминал → заменить правой частью продукции (выбор по lookahead), терминал → сопоставить с токеном и продвинуться; `ε`-продукции разрешают пустоту (`E'`, `T'`)
* **Почему работает:** FIRST/FOLLOW непересекаются — выбор продукции детерминирован одним токеном; грамматика без левой рекурсии (правые части E' и T' рекурсивны вправо) — таблица корректна; запись продукции в deriv — левая (leftmost) производная
* **Сложность:** O(n); не разбирает `'-'` (его нет в грамматике) — ожидаемое падение
* **Обобщение:** производная грамматика — параметр: из произвольной КС-грамматики без левой рекурсии и с попарно непересекающимися FIRST строятся множества FIRST/FOLLOW и таблица размера |N|×|T| (нетерминалы × терминалы) — парсер табличный, структура не зависит от грамматики; LL(k) — k токенов lookahead
* **Реализация:** `LL1Parser` (нетерминалы E/E1/T/T1/F, терминалы, стек, deriv)
* **Связь:** рекурсивный спуск — B.1 (обе — сверху-вниз, спуск — «ручной», LL(1) — табличный); LR — B.6

## **6. LR-парсеры (анализ)**
* **Определение:** разбор снизу-вверх по автомату LR(0)-пунктов: SLR(1)/LALR(1) строят таблицы действий (shift/reduce/accept) и переходов; покрывают практически все детерминированные КС-грамматики
* **Идея:** пункт `A → α·β` — «сколько продукции уже распознано»; замыкание и переходы по токенам дают автомат; таблица из автомата управляет парсером (в B.4 — упрощённый операторный случай без таблицы состояний)
* **Почему работает:** LR-свёртки (правые производные) происходят в момент, когда правая часть полностью прочитана — приоритеты и ассоциативность выражаются конфликтами таблицы
* **Сложность:** построение автомата/таблиц — O(|грамматика|²); разбор — O(n); мощности: SLR ⊂ LALR ⊂ LR(1) (таблицы растут)
* **Обобщение:** yacc/bison, генераторы парсеров — по грамматике строят LALR-таблицы
* **Реализация:** анализа нет (см. md); практический минимум — операторный shift-reduce B.4
* **Связь:** shift-reduce — B.4; рекурсивный спуск — B.1 (сверху-вниз против снизу-вверх)

# **C. ТРАНСФОРМАЦИИ И ВЫЧИСЛЕНИЯ**

## **1. Visitor Pattern (обход дерева)**
* **Определение:** универсальный обход AST с замыканиями pre/in/post; демо — печать и сбор значений листьев без изменения дерева
* **Идея:** обход — одна функция с тремя точками входа (до, между детьми, после); операции над деревом — замыкания, а не встроенные методы; унарный `~` — частный случай (один ребёнок, без in)
* **Почему работает:** разделение структуры (обход) и семантики (замыкание): одна реализация обхода, любые операции; pre-order печать — форма записи дерева
* **Сложность:** O(n); памяти — глубина рекурсии
* **Обобщение:** отделение алгоритма от структуры — интерпретаторы, трансформации (C.3, C.4), компиляция (C.5)
* **Реализация:** `TreeVisitor` (walk с pre/in/post; collect, leaf_sum)
* **Связь:** обходы деревьев — II.B; AST — A.1

## **2. Интерпретация с переменными**
* **Определение:** мини-интерпретатор строк: `"x = <expr>"` (присваивание) и `"<expr>"` (вычисление) над окружением переменных
* **Идея:** строка → токены (ввод B; детали — D.1) → AST рекурсивным спуском (B.1) → eval (A.1) с окружением; присваивание — синтаксический трюк: имя до `=` + вычисление правой части
* **Почему работает:** разделение этапов (лексика/синтаксис/семантика) делает интерпретатор композицией готовых частей
* **Сложность:** O(n) на строку
* **Обобщение:** циклы и условия — управляющие узлы AST; REPL
* **Реализация:** `Interpreter` (exec_line; trim для имени переменной)
* **Связь:** Lexer — D.1; RecursiveDescent — B.1; AST eval — A.1

## **3. Символьное дифференцирование**
* **Определение:** производная AST по переменной 'x': `d(const)=0`, `d(x)=1`, линейность, произведение, частное, степень (показатель — константа); результат — новое дерево
* **Идея:** рекурсивное применение правил; результат строится как новое дерево (не мутирует вход): `d(a·b) = da·b + a·db`, `d(a/b) = (da·b − a·db)/b²`, `d(a^b) = b·a^(b−1)·da`
* **Почему работает:** производная — композиция правил по структуре дерева; унарный минус — линейность (`d(−a) = −da`)
* **Сложность:** O(узлы исходного дерева) — но выход может расти (произведение и частное размножают узлы)
* **Обобщение:** правила для функций (sin/cos/… — цепное правило) — расширение функций в A.2; производная по любой переменной — параметр (не только 'x'); упрощение результата — C.4; численное значение производной без построения дерева — автоматическое дифференцирование C.6
* **Реализация:** `Differentiator` (diff; правила +,-,*,/,^,~)
* **Связь:** AST — A.1; упрощение — C.4

## **4. Упрощение и constant folding**
* **Определение:** свёртка константных поддеревьев и алгебраические правила (`x+0`, `x·1`, `x·0`, `x^1`, `0−x = −x`) — рекурсивно снизу вверх
* **Идея:** simplify возвращает новое дерево: сначала упрощаются дети, затем, если оба — константы, узел сворачивается в константу; правила-редукции устраняют нейтральные элементы; `~` с константой — сразу значение, двойной минус — отбрасывается
* **Почему работает:** локальные переписывания сохраняют значение (конгруэнтность); порядок снизу-вверх гарантирует, что правила применяются к уже упрощённым детям
* **Сложность:** O(n) узлов исходного дерева
* **Обобщение:** система переписывания термов (rewrite system); сокращение выражений — размер выхода
* **Реализация:** `Simplifier` (simplify, is_const)
* **Связь:** дифференцирование — C.3 (упрощает производную); constant folding — компиляторная оптимизация

## **5. Компиляция в байт-код (стековая VM)**
* **Определение:** AST → последовательность инструкций стековой машины (PUSH/ADD/SUB/MUL/DIV/POW/NEG) + интерпретатор байт-кода; компиляция — постфиксный обход (та же схема, что постфиксная запись A.1)
* **Идея:** компилятор — обход: лист → PUSH, унарный `~` → NEG, бинарный → дети + инструкция операции; VM — стек (I.C): инструкция забирает 2 (1) значения и кладёт результат
* **Почему работает:** постфиксный порядок эмиссии = порядок вычисления стековой машины; код не зависит от дерева после компиляции — исполнение линейное
* **Сложность:** компиляция O(n); исполнение O(число инструкций)
* **Обобщение:** набор инструкций I и арность каждой — параметр машины; регистры вместо стека — трехадресный код (E.2); оптимизации байт-кода (C.4 перед компиляцией)
* **Реализация:** `BytecodeCompiler` (compile/emit/run/to_string)
* **Связь:** постфикс — A.1; стеки — I.C; TAC — E.2

## **6. Автоматическое дифференцирование (forward mode)**
* **Определение:** производная выражения в точке без построения производной — двойные числа (dual numbers) `x + x'·ε` (ε² = 0): значение и производная считаются одним проходом по дереву A.2
* **Идея:** каждая операция перегружена на пару (v, d): `(u+u'ε)±(v+v'ε)` — покомпонентно, произведение — `uv + (u'v + uv')ε`, частное — `(u'v − uv')/v²`, степень — `u^v·(v'·ln u + v·u'/u)`; функции — цепное правило: `sin → cos·x'`, `log → x'/x`, `sqrt → x'/(2√x)`, `abs → x'·sign x`
* **Почему работает:** линейность двойного расширения (ε² = 0) делает производную операцией, совместимой со всеми правилами; один обход даёт и f(a), и f'(a) — в отличие от символьного дифференцирования (C.3) нет роста дерева, в отличие от численного — нет шага h
* **Сложность:** O(число узлов) на одну переменную; для производной по k переменным — k проходов (или режим с вектором d размером k)
* **Обобщение:** forward mode — частный случай обратного режима (reverse mode, backprop): при k переменных и одном выходе reverse эффективнее; высшие производные — итерирование двойного расширения (dual numbers порядка k)
* **Реализация:** `AutoDiff` (Dual v/d; eval по FunctionAST с целевой переменной)
* **Связь:** дерево выражений — A.2; символьное дифференцирование — C.3; интерпретация — C.2

# **D. ВАЛИДАЦИЯ И ПРОВЕРКА КОРРЕКТНОСТИ**

> Верификация выражения — три последовательных слоя: лексика (D.1 — корректность токенов), синтаксис (D.2 — корректность последовательности), семантика (D.3 типы, D.4 безопасность); каждый слой — отдельная функция «текст/дерево → ок/ошибка», пайплайн в F.3.

## **1. Лексический анализ (токенизация)**
* **Определение:** текст → последовательность токенов: числа (многоразрядные), идентификаторы, операторы, скобки; неизвестный символ — токен BAD с позицией; терминальный END
* **Идея:** детерминированный автомат по символам: пробел пропускается, цифра — накопление числа, буква — идентификатор, оператор — по приоритету `op_prec` (I.C); лексика отделена от синтаксиса — все парсеры (B) работают с одним потоком токенов
* **Почему работает:** регулярная природа токенов (цифры/буквы/знаки) позволяет разбивать без контекста; позиция в токене — для сообщений об ошибках
* **Сложность:** O(n)
* **Обобщение:** строки в кавычках, комментарии — расширение автомата; интернирование литералов; алфавит токенов (число классов) — параметр: регулярная природа позволяет строить автомат по правилам
* **Реализация:** `Token` (kind, lex, val, prec, pos) + `Lexer` (конструктор из строки; has_bad)
* **Связь:** приоритеты — I.C; используется во всех парсерах B и валидации D.2

## **2. Синтаксическая проверка**
* **Определение:** проверка корректности последовательности токенов: парность скобок (переиспользуется `is_balanced` из I.C), чередование операндов и операторов, отсутствие битых токенов и хвостовых операторов
* **Идея:** конечный автомат «ожидается операнд/оператор»: операнд сбрасывает флаг, оператор (кроме унарного `-`) — ставит; скобки — через баланс (I.C); BAD-токен — сразу ошибка с позицией
* **Почему работает:** выражения — чередование операндов и операторов; проверка до построения дерева отбрасывает мусор до парсинга
* **Сложность:** O(n)
* **Обобщение:** сообщения об ошибках с позицией; восстановление после ошибок (skip-токен)
* **Реализация:** `SyntaxValidator` (validate с err-сообщением)
* **Связь:** баланс скобок — I.C; Lexer — D.1; парсеры — B

## **3. Проверка типов (type checking)**
* **Определение:** типы INT/FLOAT: арифметика над числами; `/` и переменные дают FLOAT; `^` требует целого показателя (иначе ERR); инференция снизу вверх по дереву
* **Идея:** тип узла — функция типов детей: INT операнды → INT (кроме `/` → FLOAT); любой FLOAT — поднимает операцию до FLOAT; `^` с FLOAT — ошибка; переменная — FLOAT (тип неизвестен)
* **Почему работает:** инференция снизу вверх композициональна — тип корня определяется детьми рекурсивно; ERR распространяется (ни один родитель не «лечит» ошибку)
* **Сложность:** O(n)
* **Обобщение:** строгие типы с таблицей символов (E.3); приведение типов; решётка типов — параметр: любое множество T с отношением подтипов и join-операцией (правила подъёма — таблица), инференция снизу вверх не меняется
* **Реализация:** `TypeChecker` (check, name)
* **Связь:** AST — A.1; SymbolTable — E.3

## **4. Обнаружение ошибок: деление на ноль, переполнение**
* **Определение:** константные проверки: делитель-константа 0; переполнение при свёртке констант — вычисление в `__int128` с границами `long long`
* **Идея:** если оба ребёнка — константы, операция проверяется точно: сумма/разность/произведение считаются в `__int128` и сравниваются с границами; `^` — умножения с ранним выходом; рекурсивный спуск по дереву находит опасные поддеревья
* **Почему работает:** константные подвыражения вычисляются во время компиляции — переполнение и деление на 0 обнаруживаются до исполнения; рекурсия гарантирует полноту по дереву
* **Сложность:** O(n)
* **Обобщение:** анализ потока данных, замена констант; предупреждения компилятора; проверка в `__int128` — параметр точности (границы типа T вместо `long long`); предикат «опасная операция» — параметр (деление на 0, переполнение, корень из отрицательного)
* **Реализация:** `SafetyChecker` (const_div_by_zero, overflow_risk)
* **Связь:** constant folding — C.4; типы — D.3

# **E. СПЕЦИАЛИЗИРОВАННЫЕ СТРУКТУРЫ ДЛЯ ВЫРАЖЕНИЙ**

## **1. DAG выражений (общие подвыражения, CSE)**
* **Определение:** hash-consing: узел интернируется по (оператор, левый id, правый id) — листья по значению/имени; одинаковые поддеревья разделяются; число уникальных узлов падает — это common subexpression elimination
* **Идея:** сборка узлов рекурсивно: дети строятся (получают id), ключ `op/l/r` ищется в memo-таблице; найден — переиспользуем id, нет — создаём; листья — по `n<val>`/`v<name>`
* **Почему работает:** ключ узла детерминирован по детям — одинаковые поддеревья дают одинаковый ключ (инвариант хеша); DAG = дерево с разделяемыми поддеревьями
* **Сложность:** O(n) ожидаемо (хеш-таблица); память — только уникальные узлы
* **Обобщение:** интернирование строк/констант; ключ — параметр: любой узел арности k и с любыми метками (оператор, имя функции, тип) кодируется кортежем (метка, id₁..id_k) — CSE работает для любого дерева; граф вместо дерева для экономии — предшественник SSA (E.2)
* **Реализация:** `ExprDAG` (vector<Node> + unordered_map memo; build)
* **Связь:** hash-consing — `hashing.md` I; AST — A.1; TAC/SSA — E.2

## **2. Трехадресный код (TAC) и SSA**
* **Определение:** AST → линейная последовательность присваиваний `t_i = a op b`; каждый временной регистр присваивается ровно один раз (SSA-lite)
* **Идея:** ген-функция по дереву: лист — имя/константа, узел — рекурсивно дети + новая временная `t_i` с операцией; унарный минус — `t_i = -a`
* **Почему работает:** каждый узел порождает ровно одну инструкцию и один свежий регистр — SSA-свойство выполняется построением (каждый t присваивается один раз); линейная форма готова к оптимизациям и генерации
* **Сложность:** O(n); число инструкций = число узлов
* **Обобщение:** basic blocks и CFG; оптимизации (dead code, propagation) — по SSA
* **Реализация:** `ThreeAddressCode` (gen, to_string; gen_expr с нумерацией t)
* **Связь:** байт-код — C.5 (стековая VM vs регистры); DAG — E.1; AST — A.1

## **3. Таблица символов (скоупы)**
* **Определение:** иерархическая таблица: стопка скоупов, объявление в текущем, поиск — от внутреннего к внешнему (затенение имён)
* **Идея:** `vector<map<name,Entry>>`: push_scope/pop_scope меняют глубину; lookup — обратный проход по скоупам, первое совпадение; assign — запись по месту объявления (не создание)
* **Почему работает:** затенение — порядок прохода: внутренний скоуп виден раньше внешнего; RAII-подобный push/pop ограничивает время жизни имён
* **Сложность:** lookup/declare — O(скоупы) поиск (обычно O(1) на практике); память — сумма объявлений
* **Обобщение:** функции и типы в записях; линковка (разрешение имён)
* **Реализация:** `SymbolTable` (Entry, push_scope/pop_scope/declare/assign/lookup/depth)
* **Связь:** типы — D.3; интерпретатор (переменные) — C.2

# **F. ПРИМЕНЕНИЯ**

## **1. Конфигурационные языки (key = value)**
* **Определение:** парсер конфигов: строки `"key = value"`, комментарии `#` и `//`; значения — int / double / bool / строка в кавычках
* **Идея:** построчный разбор: удаление комментария, поиск `=` (ошибка с номером строки), тримминг ключа/значения, классификация значения (bool-литералы, кавычки → строка, точка → double, иначе int, ошибка → диагностика)
* **Почему работает:** регулярный формат строк (лексика простая) — разбор без парсера; тип хранится в записи Entry — потребление через get
* **Сложность:** O(строки·длина); доступ — O(1) по map
* **Обобщение:** секции `[group]`, наследование, `include`; INI/JSON — дерево значений (мост из A); множество типов значений T (int/double/bool/string/…) и правило распознавания — параметр: добавляется тип — добавляется ветвь классификации; ключ — произвольный идентификатор
* **Реализация:** `ConfigParser` (Entry, parse(istream), get; trim)
* **Связь:** Lexer — D.1 (общая лексика); F.2 — шаблоны

## **2. Шаблонизаторы (подстановка {{var}})**
* **Определение:** подстановка `{{name}}` из контекста; фильтры `{{name|upper}}`, `{{name|lower}}` — первая ступень генерации текста по данным
* **Идея:** скан текста: ищем `{{` → копируем до неё, читаем имя до `}}`, применяем фильтр (`upper`/`lower` через transform), продолжаем; незакрытая конструкция — копируется как есть
* **Почему работает:** шаблон — текст с разметкой-дырками; обработка — проход с find — позиционный стек, без дерева
* **Сложность:** O(длина шаблона + суммарный вывод)
* **Обобщение:** условия и циклы — полноценный DSL (мост к парсерам B); экранирование
* **Реализация:** `TemplateEngine` (render с контекстом map<string,string>)
* **Связь:** строки — `string.md`; конфиги — F.1

## **3. Front-end компилятора и DSL (анализ)**
* **Определение:** пайплайн компиляции: лексика (D.1) → синтаксис (B) → семантика (D.3) → дерево (A) → трансформации (C) → вывод (C.5, E.2); составление из готовых частей демонстрируется в main (конфиг + шаблон)
* **Идея:** каждый этап — функция «структура → структура» с проверкой ошибок; конвейер инвариантен по тексту (текст только в D.1)
* **Почему работает:** разделение этапов делает пайплайн переиспользуемым: та же лексика/синтаксис — другие семантики; DSL — подмножество выражений с конфигом и шаблонами
* **Сложность:** O(n) по длине входа на этап
* **Обобщение:** генерация машинного кода; макропроцессоры и препроцессоры — повторная лексика/парсинг после подстановки макроса и условной компиляции (та же схема, что F.2, но с циклом «разобрать → заменить → разобрать»); JSON/XML-парсеры — деревья значений (A как каркас)
* **Реализация:** анализа нет (см. md); части пайплайна — вся ось IX
* **Связь:** D.1→B→D.3→A→C — вся ось; персистентность — VII (деревья как значения)

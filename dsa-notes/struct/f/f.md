**VI. КОРНЕВЫЕ СТРУКТУРЫ (SQRT DECOMPOSITION)**

> **Архитектура:** `SqrtStructures` (f.cpp) — класс ветки struct, наследует `RangeQueries` (e.cpp). Вводит структуры на корневой декомпозиции: блочные разбиения массива (A), алгоритм Мо — офлайн-обработку запросов (B), дерево отрезков над блоками (C), sqrt-декомпозицию по вершинам графа и Heavy-Light Decomposition (D). Переиспользует из базы: `ParentArray` (B.9) — LCA двоичными подъёмами для Мо на деревьях (B.3); дерево отрезков `SegmentTreeIterative` (V.D.3) — агрегаты блоков в C.1 и массив позиций HLD (D.2); `LazySegTreeAdd` (V.D.6) — прибавления на цепочках HLD (D.2); целочисленные корни `DigitOps` (number-theory C.2) — `isqrt_newton` для ⌈√n⌉ (A.1–C.1) и `kth_root_newton` для ⌈n^(1/3)⌉ (B.2), без плавающей арифметики; мотив «полные куски + хвосты» — бакеты (I.D.8), Fenwick с диапазонными обновлениями (V.B.5); ленивость (V.D.6) — ленивые сдвиги блоков (A.3); обратимость операций (V.A.4) — инвариант окна Мо (B.4). Закладывает приёмы, переиспользуемые дальше: HLD — пути в графе за O(log² n) — мост в `graph.md` (LCA, суммы и прибавления на путях, ДП на деревьях); Мо — переупорядочивание запросов офлайн (мост в `technique.md`); тяжелые/лёгкие вершины — стандартный приём для графов с несимметричными степенями (задачи графов `graph.md`). Собственной арифметики не имеет: корни — готовые `DigitOps`.

> **Связи:** выбор размера блока и асимптотика окон — `analysis.md`; целочисленные корни — number-theory C.2; LCA и обходы деревьев — B.9; деревья отрезков — V.D; бакетные схемы — I.D.8; офлайн-сортировка и переупорядочивание — `technique.md`; персистентность Мо-вариантов — мост в VII.

# **Основные понятия и принципы**

* **Что это:** структуры, делящие данные на «корни» — блоки размера B ≈ √n — и обрабатывающие запросы как «полные блоки целиком + хвосты поштучно»; плюс алгоритм Мо — офлайн-переупорядочивание запросов, чтобы окно двигалось мало; плюс декомпозиции графов на тяжелые/лёгкие вершины и цепочки
* **Почему выделяется в отдельный класс:** логарифмические структуры (V) требуют агрегаты и сложный код; корневая декомпозиция даёт O(√n) простым кодом и, главное, решает задачи, где логарифм не помогает: число различных на отрезке (B.1) — логарифмической структуры нет, а Мо справляется офлайн; обновления произвольной формы (B.2), пути в дереве (B.3), суммы соседей в графе (D.1)
* **Ключевые принципы:** блоки — любая задача разбивается на крупные куски с предвычисленным агрегатом и мелкие хвосты; выбор B — стоимость B + n/B, оптимум при B = √n (A.2); окно — инвариант `[cl, cr)` поддерживается add/remove, цена — движение указателей (B); переупорядочивание — сортировка запросов уменьшает суммарное движение (B.1); «большие храним, маленькие пересчитываем» — тяжелые вершины с предвычисленными суммами (D.1); цепочки — путь разбивается на O(log n) вертикальных отрезков (D.2)
* **Как распознать:** «число различных на отрезке», «частоты», «запросов много и они офлайн» — Мо (B); «сумма/минимум на отрезке простым кодом с обновлениями» — блоки (A); «прибавление на отрезке + сумма» — A.3 или дерево отрезков; «сумма весов соседей вершины с обновлениями весов» — тяжелые/лёгкие (D.1); «сумма/прибавление на пути в дереве» — HLD (D.2)
* **Границы:** Мо — только офлайн (все запросы известны заранее); add/remove должны быть обратимыми (приходят в обратном порядке) — для суммы/частот ок; минимум в окне — нет (необратим); блоки дают O(√n), а не O(log n): на запрос ~√n элементарных операций против ~log n — при n, где √n ≫ log n, и многих запросах логарифмические структуры (V) выигрывают, при умеренных n простота кода и малая константа блока перевешивают; HLD требует статичное дерево (рёбра не меняются)

# **A. КОРНЕВАЯ ДЕКОМПОЗИЦИЯ (SQRT DECOMPOSITION)**

## **1. Sqrt Decomposition (сумма на отрезке)**
* **Определение:** массив разбит на блоки размера B (обычно B = ⌈√n⌉, параметр структуры); для каждого блока предвычислен агрегат — сумма; запрос `[l, r)`: полные блоки — суммой агрегатов O(n/B), хвосты — поштучно O(B); обновление точки — пересчёт агрегата своего блока O(1)
* **Идея:** два уровня обработки — «крупными кусками» и «по одному»; любой отрезок состоит из не более чем двух хвостов и набора целых блоков: O(B + n/B)
* **Почему работает:** предвычисление агрегатов платит один раз за блок; B + n/B минимально при B = √n — поэтому суммарно O(√n) на запрос (A.2)
* **Сложность:** построение O(n), запрос O(B + n/B) = O(√n), обновление O(1); память O(n)
* **Обобщение:** агрегат — любая ассоциативная операция (сумма, xor, min, max, gcd); для min/max/gcd обновления работают так же (пересчёт блока); операции на отрезке — A.3; ускорение полных блоков деревом отрезков — C.1
* **Реализация:** `SqrtSum` (B параметром; `build`, `update(p, x)`, `query(l, r)`, `block_size()`)
* **Связь:** «полные куски + хвосты» — мотив бакетов (I.D.8), корзин Фенвика (V.B.6), Interval Tree (V.E.2); выбор размера блока — A.2; блоки с ленивостью — A.3

## **2. Оптимальный размер блока**
* **Определение:** стоимость операций через B: запрос A.1 — B (хвосты) + n/B (полные блоки); обновление — O(1), от B не зависит; A.3: обновление тоже O(B) (пересборка хвостов)
* **Идея:** минимизация по B: A.1 — производная от B + n/B по B обращается в ноль при B = √n; A.3 при u обновлениях и q запросах — суммарно u·B + q·(B + n/B), оптимум B = √(q·n/(q+u)) — при q = u это √(n/2), при только запросах √n, при u ≫ q блоки мельче (обновления дороги)
* **Почему работает:** B — параметр конструктора: структуру можно настроить под распределение операций конкретной задачи, не меняя код
* **Сложность:** A.1 — O(√n) на запрос при любом разумном B; A.3 — O(√n) при q ~ u
* **Реализация:** B — аргумент конструктора `SqrtSum`, `SqrtRangeAdd`, `SqrtSegTree` (по умолчанию ⌈√n⌉ — целочисленным корнем `isqrt_newton`, number-theory C.2)
* **Связь:** анализ сумм и производных — `analysis.md`; тюнинг под смешанные запросы — C.2

## **3. Sqrt Decomposition: прибавление и сумма на отрезке**
* **Определение:** прибавление x на `[l, r)` + сумма на `[l, r)`: полные блоки — ленивый сдвиг add[b] += x за O(1); хвосты — поштучно с пересборкой суммы блока O(B)
* **Идея:** ленивость на уровне блоков: значение элемента = a[i] + add[i/B]; сумма полного блока = sum[b] + add[b]·B; пересборка нужна только хвостам
* **Почему работает:** любой отрезок — два хвоста O(B) + полные блоки O(n/B) — обе операции O(√n); ленивый сдвиг избавляет от применения к блоку целиком
* **Сложность:** `range_add` и `range_sum` — O(B + n/B) = O(√n) каждая; память O(n)
* **Обобщение:** «применить к блоку целиком за O(1)» — тот же мотив, что ленивые операции дерева отрезков (V.D.6) и Fenwick с диапазонными обновлениями (V.B.5); обратная задача — снятие лени: точечный запрос значения — a[i] + add[i/B]
* **Реализация:** `SqrtRangeAdd` (B параметром; `range_add(l, r, x)`, `range_sum(l, r)`)
* **Связь:** ленивость — V.D.6; выбор B — A.2

# **B. АЛГОРИТМ МО**

## **1. Стандартный Мо (сортировка запросов, два указателя)**
* **Определение:** офлайн-обработка запросов к подотрезкам: запросы сортируются по (номер блока левого конца l/B, правый конец r); окно `[cl, cr)` двигается двумя указателями: расширение — add, сужение — remove; в момент, когда окно равно запросу, ответ фиксируется
* **Идея:** в пределах одного блока l правый указатель движется только вправо — суммарно O(n) на блок; левый дёргается в пределах блока — O(B) на запрос: итого O(n·n/B + q·B) → при B = √n — O((n + q)·√n)
* **Почему работает:** сортировка превращает хаотичное движение в монотонное по r внутри блока; «зигзаг» (чётные блоки — r по возрастанию, нечётные — по убыванию) экономит возвраты между блоками
* **Сложность:** сортировка O(q log q), обработка O((n + q)·√n); память O(n)
* **Обобщение:** add/remove — параметры (B.4); окно произвольного инварианта: сумма, частоты, число различных
* **Реализация:** `MoSolver::run(n, queries, add, remove, save)` — раннер с функциями-параметрами
* **Связь:** переупорядочивание запросов — мост в `technique.md`; окно как инвариант — B.4; офлайн-ограничение — граница метода

## **2. Мо с обновлениями (третья координата времени)**
* **Определение:** обновления значения `(pos, from, to)`; запрос — тройка `(l, r, t)`, где t — сколько обновлений применено до запроса; сортировка по (l/B, r/B, t); окно движется по l, r и по времени — применение/откат обновлений
* **Идея:** движение времени: применить обновление — если позиция в окне, сначала remove(pos), затем смена значения в массиве, затем add(pos); откат — симметрично (from ↔ to); размер блока B = n^(2/3): число блоков по каждой оси ~ n^(1/3), движение каждого указателя — O(q·n^(2/3) + n^(5/3))
* **Почему работает:** третья координата не меняет схему — время монотонно внутри пары (l-блок, r-блок); суммарное движение t-указателя — O(q·n^(2/3) + n·n^(2/3))
* **Сложность:** O(n^(5/3)) ~ O(q·n^(2/3)) при q ~ n; сортировка O(q log q)
* **Обобщение:** обновления произвольного вида — функции apply (B.4); значения замены (from, to) известны заранее — офлайн
* **Реализация:** `MoWithUpdates::run(n, queries, updates, arr, add, remove, save)` — `arr` обязан быть массивом в состоянии при t = 0 (откат полагается на from); изменения вносит сам раннер; B = ⌈n^(1/3)⌉² — кубический корень `kth_root_newton` (number-theory C.2)
* **Связь:** откат — мотив III.A.6 (RollbackDSU); время как третья координата — раздел VII

## **3. Мо на деревьях (эйлеров порядок + LCA)**
* **Определение:** путь u–v в дереве сводится к отрезку в эйлеровом порядке: каждая вершина входит дважды (tin — появление, tout — исчезновение); путь — интервал с переключением вершин (toggle: нечётное вхождение — активна)
* **Идея:** если lca(u, v) = u (u — предок v) — интервал [tin[u], tin[v]]; иначе [tout[u], tin[v]] (u — вершина с меньшим tin) плюс lca отдельно; в интервале каждая вершина пути встречается ровно один раз, прочие — дважды (гасятся toggle-ом)
* **Почему работает:** эйлеров обход даёт «линеаризацию» путей: вершины поддерева — непрерывный отрезок (V.D, HLD — та же идея); LCA нужен один раз на запрос — двоичные подъёмы (B.9) за O(log n)
* **Сложность:** как B.1 + O(log n) на LCA (препроцессинг O(n log n)); окно — 2n позиций
* **Обобщение:** значения на пути — частоты/суммы; поддерево — отрезок [tin, tout] без эйлеровых трюков
* **Реализация:** `MoOnTree` (переиспользует `ParentArray` — LCA; `path_to_interval(u, v)` → `[l, r)` + lca; `run` с toggle)
* **Связь:** LCA — B.9; линеаризация поддеревьев — D.2 (HLD), V.D; пути в деревьях — `graph.md`

## **4. Обобщение: add/remove как параметр (инвариант окна)**
* **Определение:** раннер Мо не знает, что считает окно: add(p), remove(p), save(id) — параметры-функции; инвариант окна (частоты, сумма, что угодно) живёт в вызывающем коде и его лямбдах
* **Идея:** раннер гарантирует порядок вызовов: окно [cl, cr) инвариантно между запросами; расширение/сужение — add/remove; фиксация ответа — save
* **Почему работает:** обратимость: remove приходит в точном обратном порядке, чем add — любое состояние, поддерживаемое парой «добавить/убрать элемент», подходит; необратимые (минимум без частот) — нет
* **Сложность:** не меняется; цена — вызовы функций (инлайнятся)
* **Реализация:** `MoSolver::run`, `MoWithUpdates::run`, `MoOnTree::run` — все три принимают add/remove/save функциями
* **Связь:** обратимость — инверсия (V.A.4); параметризация операциями — тот же мотив, что V.D.9 (SegmentTreeGeneric)

# **C. ДЕРЕВО ОТРЕЗКОВ С КОРНЕВОЙ ДЕКОМПОЗИЦИЕЙ**

## **1. Дерево отрезков над блоками**
* **Определение:** блочные агрегаты (A.1) собраны в дерево отрезков: запрос по полным блокам — O(log(n/B)) вместо O(n/B); хвосты — поштучно O(B); обновление — пересборка блока O(B) + дерево O(log(n/B))
* **Идея:** «дерево деревьев» в миниатюре: блок — «лист» второго уровня; длинные запросы ускоряются деревом, короткие — дёшевы по хвостам
* **Почему работает:** число блоков n/B — дерево над ними даёт логарифм; B — параметр компромисса между скоростью длинных и коротких запросов (C.2)
* **Сложность:** query/update — O(B + log(n/B)); при B = √n — O(√n) с меньшей константой, чем A.1, для длинных запросов
* **Обобщение:** агрегат — любая ассоциативная операция (дерево V.D.3); ленивые операции на блоках (A.3) совместимы с деревом
* **Реализация:** `SqrtSegTree` (B параметром; переиспользует `SegmentTreeIterative` (V.D.3); `update(p, x)`, `query(l, r)`)
* **Связь:** дерево над блоками — мотив V.B.4, V.D.12; выбор B — A.2, C.2

## **2. Оптимизация для смешанных запросов**
* **Определение:** если запросы/обновления неоднородны (много коротких, реже длинные; много обновлений, реже запросы), выбор структуры и B настраивается под доли
* **Идея:** короткий запрос стоит только хвостов O(B) — мелкие B ускоряют короткие и дорожают длинные (через log(n/B) — слабо); доля обновлений двигает оптимум (A.2); крайние случаи: только длинные запросы без обновлений — префиксные суммы (V.A); только короткие — обычный массив
* **Почему работает:** стоимость — сумма по типам операций с весами-частотами; B подбирается перебором нескольких значений или формулой A.2
* **Сложность:** оптимум B — по формуле A.2 с долями операций
* **Реализация:** B — параметр `SqrtSegTree`; выбор между A.1 / C.1 / V.D — анализ долей
* **Связь:** анализ — `analysis.md`; выбор между структурами — мотив раздела V

# **D. SQRT ДЕКОМПОЗИЦИЯ ПО БЛОКАМ (ГРАФЫ)**

## **1. Тяжелые и легкие вершины**
* **Определение:** граф с m рёбрами; тяжёлая вершина — степень > √(2m), лёгкая — иначе; тяжёлых не больше √(2m) ≤ 2√m (сумма степеней 2m, каждый тяжёлый «стоит» > √(2m)); задача: обновление веса вершины `(x, d)` + запрос суммы весов соседей v
* **Идея:** для тяжёлых хранится S[v] — сумма весов всех соседей: при обновлении (x, d) S[v] += d для каждого тяжёлого соседа v вершины x (перебор соседей x, O(deg x)); запрос тяжёлой — S[v] за O(1); запрос лёгкой — пересчёт по списку соседей O(deg v) ≤ O(√(2m))
* **Почему работает:** обновление платит только за тяжёлых соседей (их мало), запрос — либо O(1) (тяжёлая), либо дёшев по определению (лёгкая): обе стороны O(√m)
* **Сложность:** построение O(n + m), обновление O(√m) (перебор соседей), запрос O(√m); память O(n + m)
* **Обобщение:** «большие храним, маленькие пересчитываем» — общий приём: инцидентность по лёгким/тяжёлым применяется к любым суммам по соседям, xor, число соседей с свойством; динамические рёбра — тяжело (нужна поддержка S)
* **Реализация:** `HeavyLightVertices` (`build(n, edges, weights)`, `add_weight(x, d)`, `neighbor_sum(v)`)
* **Связь:** число тяжёлых ≤ 2√m — тот же подсчёт, что «много корней в бакетах» (I.D.8); HLD — вертикальные цепочки той же природы (D.2)

## **2. Heavy-Light Decomposition (HLD)**
* **Определение:** разбиение вершин дерева на вертикальные цепочки: heavy-ребро — к ребёнку с максимальным размером поддерева (при равенстве — любой); вторая DFS кладёт цепочки в единый массив pos (тяжёлый ребёнок сразу за родителем); поверх pos — дерево отрезков (V.D)
* **Идея:** путь u–v разбивается на O(log n) цепочек: пока head[u] ≠ head[v] — обрабатываем цепочку более глубокого head и прыгаем вверх; внутри цепочки — один отрезок дерева отрезков: итого O(log n) цепочек × O(log n) дерево = O(log² n)
* **Почему работает:** переход к head-родителю как минимум удваивает размер поддерева (иначе ребро было бы heavy) — цепочек на пути O(log n); поддерево — непрерывный отрезок pos (тяжёлые дети подряд) — запрос за O(log n)
* **Сложность:** построение O(n), путь O(log² n), поддерево O(log n); память O(n)
* **Применение:** суммы/минимумы на путях, прибавления на пути, взвешенные рёбра (вес ребра — на ребёнке), задачи о путях — мост в `graph.md` (взвешенные пути, диаметр, ДП на деревьях)
* **Реализация:** `HeavyLightDecomposition` (переиспользует `LazySegTreeAdd` (V.D.6) — прибавления и суммы; `path_query(u, v)`, `path_add(u, v, x)`, `sub_query(v)`)
* **Связь:** LCA — B.9 (та же линеаризация глубин); дерево отрезков — V.D; эйлеров порядок — B.3; графы — `graph.md`

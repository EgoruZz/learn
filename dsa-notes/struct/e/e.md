# **Основные понятия и принципы**

* **Что это:** статическая или обновляемая структура над массивом/матрицей, отвечающая на запросы о подотрезках и прямоугольниках: сумма, минимум/максимум, gcd, число элементов ≤ x, k-я статистика; обновления — по точке (B, D) или по отрезку (D.5–D.8)
* **Почему выделяется в отдельный класс:** запросы об отрезках — самый частый примитив задач (префиксы, RMQ, динамика на диапазонах); наивный проход по отрезку за O(n) заменяется структурой с O(log n) — константный/логарифмический ответ на стандартные вопросы
* **Ключевые принципы:** префикс и разность — сумма по отрезку = разность префиксов (A); дерево-«массив» — полное дерево с агрегатом в узле (D), lowbit-индексация — префикс как сумма O(log n) блоков (B); ленивость — откладывать применение операции до спуска (D.6); покрытие блоками — любой отрезок разбивается на O(log n) «канонических» блоков; статичность — Sparse Table платит отсутствием обновлений за O(1)-запрос (C)
* **Как распознать:** «сумма/минимум/максимум на отрезке», «обновить элемент и спросить диапазон», «сколько элементов ≤ x на подотрезке», «k-й по сумме», «максимум в точке среди прямых» — структуры запросов; «только построить и спрашивать» — префиксы/Sparse Table (A, C); «с обновлениями» — Fenwick/дерево отрезков (B, D); «постоянные обновления + запросы» — дерево отрезков с ленивыми операциями (D.6–D.10)
* **Границы:** префиксные суммы и Sparse Table не поддерживают обновления (для обновлений — B, D); Sparse Table требует идемпотентную операцию, для неидемпотентных — Disjoint ST (C.5) или дерево отрезков (D); Fenwick для range-query требует обратимую операцию (сумма — да; min/max — только префиксные с ограничениями B.2/B.3); дерево отрезков универсален, но дороже в коде и памяти

# **A. ПРЕФИКСНЫЕ СУММЫ**

## **1. Prefix Sum (1D)**
* **Определение:** `p[k] = a[0] + … + a[k−1]` (p[0] = 0); сумма на полуинтервале `[l, r)` — `p[r] − p[l]`
* **Идея:** один проход слева направо накапливает все префиксы; любой отрезок — разность двух префиксов (включения-исключения в 1D)
* **Почему работает:** префиксные суммы — обратная операция к поточечной разности: «сумма на отрезке» = «префикс до r» − «префикс до l» — достаточно двух точек
* **Сложность:** построение O(n), запрос O(1), память O(n)
* **Обобщение:** любая ассоциативная операция с обратным элементом (сумма по модулю, xor); для операций без обратного элемента (min, gcd) — Sparse Table (C)
* **Реализация:** `PrefixSum1D` (`build`, `sum(l, r)` = `p[r] − p[l]`)
* **Связь:** включения-исключения — A.2, A.3; разность — инверсия, основа Difference Array (A.4); «префикс с обновлениями» — мост в B

## **2. 2D Prefix Sum (включения-исключения прямоугольника)**
* **Определение:** `P[x][y]` — сумма подматрицы `[0, x) × [0, y)`; сумма прямоугольника — включения-исключения по 4 углам: `P[x2][y2] − P[x1][y2] − P[x2][y1] + P[x1][y1]`
* **Идея:** построение — 1D-префикс по строкам, затем по столбцам (или наоборот); каждый элемент матрицы отвечает за «угол» прямоугольника
* **Почему работает:** включения-исключения: прибавили весь угол, вычли лишние два угла, вернули дважды вычтенный пересекающийся
* **Сложность:** построение O(n·m), запрос O(1), память O(n·m)
* **Обобщение:** k измерений — включения-исключения по 2^k слагаемых (A.3)
* **Реализация:** `PrefixSum2D` (`build`, `sum(x1, y1, x2, y2)`)
* **Связь:** прямоугольники — мотив B.4 (2D Fenwick), C.4 (2D Sparse Table), D.12 (2D дерево отрезков); включения-исключения — комбинаторика

## **3. 3D Prefix Sum (обобщение на k измерений)**
* **Определение:** `P[x][y][z]` — сумма параллелепипеда `[0, x) × [0, y) × [0, z)`; запрос — включения-исключения по 2³ = 8 слагаемых: знак — по чётности числа «нижних» границ (угол с чётным числом нижних границ прибавляется, с нечётным — вычитается)
* **Идея:** построение — три прохода 1D-префиксов по каждой оси; запрос — сумма по всем 8 углам со знаками включения-исключения
* **Почему работает:** включения-исключения в k измерениях дают 2^k слагаемых (каждое — точка-угол), знак — минус за каждую «нижнюю» границу, итог — число нижних границ по модулю 2
* **Сложность:** построение O(n·m·k), запрос O(1), память O(n·m·k)
* **Обобщение:** k измерений — рекурсивно применяется A.1 по каждой оси; слагаемых 2^k — рост экспоненциальный, для больших k нужны структуры с логом (B.4, D.12)
* **Реализация:** `PrefixSum3D` (кубы `P`, включения-исключения по 8 углам)
* **Связь:** 2^k слагаемых — тот же мотив, что битовые маски; экспоненциальный рост — граница метода

## **4. Difference Array (разностный массив)**
* **Определение:** `d[i] = a[i] − a[i−1]` (d[0] = a[0]); прибавление x на `[l, r)` — `d[l] += x`, `d[r] −= x`; точечный запрос `a[i]` — префиксная сумма `d`
* **Идея:** разностный массив — «дифференциал» префиксной суммы: отрезковая операция в `a` становится точечной в `d`; восстановление `a` — обратным проходом (интегрированием)
* **Почему работает:** операция «прибавить x на отрезке» линейна — её можно разложить на две точечные дельты на концах; префиксная сумма дельт равна итоговому сдвигу
* **Сложность:** обновление O(1), восстановление/точечный запрос O(n) (либо O(1) с префиксной суммой на лету)
* **Обобщение:** 2D-разность — дельты по 4 углам (включения-исключения A.2); разностный массив — основа Fenwick с отрезковыми обновлениями (B.5)
* **Реализация:** `DifferenceArray` (`add(l, r, x)`, `value(i)` через префикс, `restore()`)
* **Связь:** инверсия префиксной суммы — A.1; дельты на концах — тот же мотив, что B.5

## **5. Prefix Sum with Updates (переход к Fenwick V.B)**
* **Определение:** префиксные суммы не выдерживают точечных обновлений: изменение `a[i]` требует пересборки всех `p[k], k ≥ i` — O(n) на обновление
* **Идея:** задача «обновление точки + запрос суммы на отрезке» — ровно то, что решает дерево Фенвика (B): префикс остаётся, но хранится деревом, пересчитываемым за O(log n)
* **Сложность:** пересборка префиксов — O(n) на обновление; Fenwick — O(log n) (раздел B)
* **Обобщение:** «обновление + запрос» — критерий выбора между A (без обновлений) и B/D (с обновлениями)
* **Реализация:** мост в B.1 (в main — сравнение пересборки префиксов и Fenwick на одинаковой серии)
* **Связь:** Fenwick (B) — префикс с обновлениями; дерево отрезков (D) — полная замена для любых операций

# **B. ДЕРЕВО ФЕНВИКА (FENWICK TREE / BINARY INDEXED TREE)**

## **1. Standard Fenwick Tree (Point Update, Range Query)**
* **Определение:** `p[i]` хранит сумму на полуинтервале `(i − lowbit(i), i]` (индексы 1..n, `lowbit(i) = i & −i`); префиксная сумма — сумма по lowbit-цепочке `i, i − lowbit(i), …`; обновление точки — подъём `i, i + lowbit(i), …`
* **Идея:** каждый индекс «владеет» блоком из `lowbit(i)` элементов — число блоков в префиксе = число битов индекса; обновление элемента трогает ровно те узлы, чьи блоки его содержат
* **Почему работает:** любое число 1..n разлагается на непересекающиеся lowbit-блоки ровно по битам двоичной записи — сумма блоков покрывает префикс без пропусков; подъём по `i += lowbit(i)` проходит ровно по владельцам точки
* **Сложность:** `add`/запрос префикса — O(log n), сумма на `[l, r)` — разность двух префиксов; построение — O(n log n) (или O(n) прибавлением `p[i + lowbit(i)] += p[i]`)
* **Обобщение:** операция — сумма (обратимая); для min/max — B.2/B.3; индексы 1..n — сдвиг на 1 от 0-индексации
* **Реализация:** `Fenwick` (`p` размера n+1; `add(i, x)` (1-индексация), `prefix_sum(i)`, `sum(l, r)`)
* **Связь:** префикс с обновлениями — A.5; lowbit — битовые приёмы IV.C; блоки-цепочки — тот же мотив, что степени двойки в C

## **2. Maximum Fenwick Tree**
* **Определение:** максимум на префиксе `[1, i]`; lowbit-цепочка даёт «максимум из O(log n) блоков», каждый узел хранит максимум своего блока
* **Границы:** обновления, только не ухудшающие значения (увеличение или присваивание большего): уменьшение элемента не пересчитывает максимум выше — для уменьшений нужны дерево отрезков (D) или пересборка
* **Почему работает:** при монотонных вверх обновлениях узел `p[i]` пересчитывается перезаписью; запрос максимума префикса — максимум по lowbit-блокам, без пересечений
* **Сложность:** `add`/запрос — O(log n)
* **Обобщение:** ограничение «только вверх» — общий мотив max-структур (монотонный стек I.C.4 — та же монотонность)
* **Реализация:** `FenwickMax` (обновление максимумом на подъёме)
* **Связь:** max-запросы — B.3 (зеркально), D.9; монотонность — I.C.4

## **3. Minimum Fenwick Tree**
* **Определение:** минимум на префиксе `[1, i]`; зеркально B.2 — работает при обновлениях, только не увеличивающих значения
* **Идея:** низlowbit-цепочка — минимум по блокам; обновление точки — перезапись минимума на подъёме
* **Границы:** увеличение элемента не поддерживается — для произвольных обновлений нужен дерево отрезков (D)
* **Сложность:** `add`/запрос — O(log n)
* **Реализация:** `FenwickMin` (обновление минимумом на подъёме)
* **Связь:** пара max/min — B.2; min-запросы на отрезке без ограничений — C.1 (статический) или D

## **4. 2D Fenwick Tree (вложенные деревья)**
* **Определение:** внешний Fenwick по оси x, в каждой его вершине — внутренний Fenwick по оси y: точка (x, y) живёт во всех внешних узлах, покрывающих x, и в каждом — во всех внутренних, покрывающих y
* **Почему работает:** обновление точки — O(log n) внешних узлов × O(log n) внутренних; запрос прямоугольника — включения-исключения (A.2) по 4 префиксам вложенных деревьев
* **Сложность:** обновление и запрос — O(log² n); память O(n·m) (или разреженно — B.6); обобщение на k измерений — O(log^k n) вложенностью k деревьев
* **Реализация:** `Fenwick2D` (вектор Fenwick-ов по строкам; `add(x, y, v)`, `sum(x1, y1, x2, y2)`)
* **Связь:** вложенность — мотив «дерево деревьев»: B.6, D.12, E.1; прямоугольники — A.2

## **5. Fenwick Tree with Range Updates**
* **Определение:** отрезковые обновления через разностный массив (A.4): Range Update / Point Query — один Fenwick по `d[i]` (`add(l, +x)`, `add(r, −x)`, точка — `prefix_sum(i)`); Range Update / Range Query — два Fenwick: `B1` по `d[i]` и `B2` по `i·d[i]`
* **Почему работает:** сумма на `[1..x]` после сдвигов — `(x+1)·Σd[i] − Σ i·d[i]` — две префиксные суммы разностного массива, обе поддерживаются за O(log n)
* **Сложность:** обновление и запрос — O(log n) в обоих режимах
* **Обобщение:** режим — параметр (точка/отрезок по каждой из осей: обновления и запросы); комбинации «точка-точка» (B.1), «отрезок-точка», «отрезок-отрезок»
* **Реализация:** `FenwickRangeUpdatePointQuery` (один Fenwick-разность), `FenwickRangeUpdateRangeQuery` (два Fenwick)
* **Связь:** разностный массив — A.4; «два дерева под одну сумму» — приём двойной суммы (мотив II.G.2)

## **6. Fenwick Tree on Fenwick Tree**
* **Определение:** «дерево на дереве» — разреженный вариант B.4: внутренние Fenwick создаются по требованию (только для реально обновлявшихся строк), вместо полной матрицы n×n — внешний Fenwick с хэш-таблицами/словарями во внутренних узлах
* **Почему:** для разреженных обновлений (мало точек на большом поле) полная память O(n·m) избыточна; на лету создаётся O(число обновлений · log n) внутренних узлов
* **Сложность:** обновление/запрос — O(log² n) (map-поиски по lowbit-цепочкам); память — O(обновлений · log n); плотный вариант без map — B.4
* **Обобщение:** то же «дерево деревьев», что D.12 (2D дерево отрезков) и E.1 (Range Tree), но в разреженном режиме
* **Реализация:** `FenwickOnFenwick` (внешний Fenwick, внутренние — `map`-узлы по y; `add(x, y, v)`, `sum(x1, y1, x2, y2)`)
* **Связь:** разреженность — мотив динамических структур (D.5); вложенные деревья — B.4

## **7. Поиск k-го по сумме за O(log n)**
* **Определение:** по дереву Фенвика с неотрицательными весами найти наименьший индекс `i` с `prefix_sum(i) ≥ k` (порядковая статистика по значению: индексы — значения, веса — количества)
* **Идея:** бинарный спуск по степеням двойки: `idx` идёт от старшей степени вниз, прибавляет шаг, если `p[idx + step] < k`, и вычитает накопленное — заканчивает на индексе, где префикс ≥ k
* **Почему работает:** узел `p[i]` покрывает блок `(i − lowbit(i), i]` — спуск по степеням двойки перебирает блоки в порядке старшинства, как бинарный поиск по «весовым» битам; корректно при весах ≥ 0 (монотонность префиксов)
* **Сложность:** O(log n) — один проход по степеням двойки
* **Обобщение:** k-я статистика — тот же вопрос, что kth в Merge Sort Tree (E.5) и порядковые статистики (II.G.2); спуск — битовые приёмы (IV.C)
* **Реализация:** `Fenwick::kth(k)` (возвращает индекс; требует веса ≥ 0)
* **Связь:** бинарный спуск — B.7 ↔ E.5, II.G.2; низlowbit-цепочка — B.1

# **C. РАЗРЕЖЕННАЯ ТАБЛИЦА (SPARSE TABLE)**

## **1. Sparse Table для RMQ (Range Minimum Query)**
* **Определение:** `st[j][i]` — минимум на `[i, i + 2^j)`; запрос минимума на `[l, r)` — минимум двух блоков: `st[k][l]` и `st[k][r − 2^k]`, где `k = ⌊log₂(r − l)⌋`
* **Идея:** предвычисление всех блоков длины степени двойки; любой отрезок покрывается двумя такими блоками (с пересечением) — корректность за счёт идемпотентности `min`
* **Почему работает:** `min(x, x) = x` — пересечение двух покрытий не портит ответ; `st[j][i] = min(st[j−1][i], st[j−1][i + 2^{j−1}])` — построение по половинкам
* **Сложность:** построение O(n log n), запрос O(1), память O(n log n); таблица логарифмов `lg[]` предвычисляется
* **Границы:** статическая структура — обновлений нет (для обновлений — D); только идемпотентные операции (C.3)
* **Реализация:** `SparseTableRMQ` (`lg`-таблица, `build`, `query(l, r)`)
* **Связь:** RMQ — мост в `graph.md` (LCA через RMQ); статичность — A.1

## **2. Sparse Table для GCD**
* **Определение:** та же схема с операцией gcd: `st[j][i]` — gcd на `[i, i + 2^j)`; запрос — gcd двух блоков
* **Почему работает:** gcd — ассоциативна и идемпотентна (`gcd(x, x) = x`) — требование C.3 выполнено
* **Сложность:** построение O(n log n) (с учётом стоимости gcd — каждый уровень O(n) операций), запрос O(1)
* **Реализация:** `SparseTableGCD` (запрос — `gcd(st[k][l], st[k][r − 2^k])`)
* **Связь:** gcd как моноид — III.A.4; идемпотентность — C.3

## **3. Sparse Table для произвольных идемпотентных операций**
* **Определение:** операция `f` — параметр: требования — ассоциативность и идемпотентность (`f(x, x) = x`); запрос — `f` двух блоков
* **Почему работает:** идемпотентность — ровно то условие, при котором пересекающиеся покрытия допустимы: `f` пересечения равна одному значению
* **Сложность:** построение O(n log n) применений `f`, запрос — O(1)
* **Обобщение:** параметризация операции — мотив B.2/B.3 (max/min), D.9 (массовые операции дерева отрезков); неидемпотентные — C.5 или D
* **Реализация:** `SparseTableGeneric` (`f` — `std::function`, `build`, `query`)
* **Связь:** моноид и агрегаты — III.A.4; параметризация — тот же приём, что компаратор в IV.A.3

## **4. Двумерная Sparse Table**
* **Определение:** `st[j1][j2]` — минимум на прямоугольнике `2^j1 × 2^j2`; запрос минимума в прямоугольнике — минимум по 4 углам-блокам (по два блока на ось)
* **Идея:** построение — по осям независимо: сначала 1D-таблицы по строкам, затем по столбцам; запрос — включения-исключения заменяются на 4 блока (идемпотентность)
* **Сложность:** построение O(n·m·log n·log m), запрос O(1), память O(n·m·log n·log m)
* **Границы:** прямоугольники с idempotentной операцией; обновлений нет
* **Реализация:** `SparseTable2D` (`query(x1, y1, x2, y2)`)
* **Связь:** прямоугольники — A.2, B.4, D.12; 4 блока вместо включений-исключений — C.1

## **5. Disjoint Sparse Table (неидемпотентные операции)**
* **Определение:** для ассоциативных, но не идемпотентных операций (сумма): предвычисление «суффиксов и префиксов внутри блоков» по уровням дерева; запрос `[l, r)` — склейка суффикса левого блока и префикса правого на уровне, где `l` и `r` попадают в разные блоки
* **Идея:** для каждого уровня (блоки длины 2^j) в каждой середине блока хранятся префиксы и суффиксы; уровень `k = ⌊log₂(l xor (r−1))⌋` — старший отличающийся бит: на нём середина блока лежит строго между `l` и `r`; `[l, r)` = суффикс левой половины блока + префикс правой — покрытие без пересечений
* **Почему работает:** на уровне разделения середина лежит между `l` и `r` — суффикс и префикс склеиваются точно по `[l, r)`; пересечения нет — идемпотентность не нужна, достаточно ассоциативности
* **Сложность:** построение O(n log n), запрос O(1) (одна операция `lg`), память O(n log n)
* **Границы:** статическая структура; обновлений нет
* **Реализация:** `DisjointSparseTable` (сумма на `[l, r)`; уровни-массивы суффиксов/префиксов)
* **Связь:** общие предки по уровням — мотив LCA (`graph.md`); блочные уровни — D (дерево отрезков)

## **6. Sparse Table с координатным сжатием (для разреженных точек)**
* **Определение:** позиции запросов/обновлений — разреженное подмножество большого диапазона: координатное сжатие (сортировка уникальных координат + индексация) сводит таблицу к числу уникальных позиций `m`, после чего работает обычная 1D Sparse Table (C.1–C.3)
* **Идея:** сбор уникальных координат всех точечных операций; сжатие — `lower_bound` по отсортированному вектору; значения заполняются на сжатых индексах (между ними — «пусто», заполнение нейтралом/растяжкой для RMQ)
* **Почему работает:** запросы обращаются только к сжатым координатам — маппинг `координата → индекс` точен; диапазон `[l, r)` запрашивается по индексам границ
* **Сложность:** сжатие O(m log m) (сортировка), построение O(m log m), запрос O(1); память O(m log m) — в отличие от O(U log U) по всему универсуму U
* **Границы:** только статический набор координат (онлайн-появление новых — к динамическому дереву D.5 или D.5.1); идемпотентная операция (неидемпотентная — C.5)
* **Реализация:** `SparseTableCompressed` (сжатие координат, RMQ на сжатых позициях)
* **Связь:** сжатие координат — тот же приём, что D.5.1; статичность — C.1

# **D. ДЕРЕВО ОТРЕЗКОВ (SEGMENT TREE)**

## **1. Segment Tree (на массиве)**
* **Определение:** полное дерево в массиве по куча-индексации (II.A.2): листья — элементы, внутренние узлы — свёртка детей; `left/right/has_left` унаследованы от `HeapIndexedTree`; хранилище — `4n` вершин (разреженный полный интервал гарантирует листья на глубине ⌈log₂n⌉)
* **Идея:** построение — рекурсивно снизу вверх; запрос `[l, r)` — рекурсивный спуск, покрывающий отрезок O(log n) узлами; обновление точки — путь от листа к корню
* **Почему работает:** каждый запрос собирается из непересекающихся канонических узлов — ровно O(log n) на любой отрезок; обновление меняет только один путь — O(log n) узлов
* **Сложность:** построение O(n), обновление/запрос O(log n), память O(n)
* **Обобщение:** операция — параметр (сумма/min/max/gcd — D.9); неидемпотентные и необратимые — в отличие от C, любые ассоциативные
* **Реализация:** `SegmentTreeArray` (наследует `HeapIndexedTree`; `build`, рекурсивные `update(i, x)`, `query(l, r)`)
* **Связь:** куча-индексация — II.A.2; дерево в массиве — тот же мотив, что бинарная куча (IV.A.1); неидемпотентность — C.5

## **2. Segment Tree (на указателях)**
* **Определение:** узлы-структуры `{l, r, val, left, right}` с явными границами `[l, r)`; вершины создаются рекурсивно при построении
* **Идея:** каждый узел «знает» свой отрезок — рекурсия не передаёт границы как параметры, а хранит их в узле; дети — указатели
* **Почему работает:** явные границы и ссылки — гибкость: база для динамического (D.5) и персистентного (D.11) деревьев, где узлы создаются по требованию
* **Сложность:** те же O(log n) на операцию; память O(n) узлов
* **Обобщение:** представление — параметр выбора: массив (D.1), указатели (D.2), итеративный (D.3)
* **Реализация:** `SegmentTreePointers` (узел с `l, r, sum, left, right`; рекурсивные `update`, `query`)
* **Связь:** динамическое дерево — D.5; персистентность — D.11; указательные деревья — II

## **3. Non Recursive Segment Tree**
* **Определение:** итеративный вариант: листья на местах `[n, 2n)` (n — степень двойки), внутренние — свёртка детей; запрос — два указателя `l, r` с подъёмом по `l/2, r/2` и попеременным включением крайних узлов; обновление — путь от листа к корню
* **Идея:** «полуинтервальная» техника: `l` и `r` — границы, сдвигаемые вверх; при нечётности `l` узел включается и сдвигается, `r` аналогично (полуоткрытый `[l, r)`)
* **Почему работает:** подъём указателей сохраняет инвариант «узлы между `l` и `r` покрывают остаток запроса» — каждая итерация отрезает по одному узлу с краёв, всего O(log n) шагов
* **Сложность:** построение O(n), запрос/обновление O(log n); без рекурсии — меньшая константа
* **Обобщение:** операция — параметр (D.9); спуск к k-му — приём D.4
* **Реализация:** `SegmentTreeIterative` (`n` — степень двойки, массив `2n`; `update(i, x)`, `query(l, r)`)
* **Связь:** дерево в массиве — D.1; техника двух указателей — деки и стеки (I.C–D)

## **4. Segment Tree Other: спуск к k-му и другие приёмы**
* **Определение:** прочие приёмы дерева отрезков: бинарный спуск к k-му по сумме (порядковая статистика, как B.7, но по дереву), построение по уровням (heapify-стиль, IV.A.2), запросы «сверху» по покрытиям (для операций без разности)
* **Идея:** kth-спуск: начиная с корня, идём к листу: если `sum[left] ≥ k` — влево, иначе `k −= sum[left]` и вправо — O(log n); уровень за уровнем — канонические узлы запроса
* **Почему работает:** сумма левого ребёнка — «сколько элементов лежит левее» — спуск по взвешенному дереву, как бинарный поиск по весам
* **Сложность:** kth — O(log n); прочие приёмы — те же оценки
* **Реализация:** `SegmentTreeIterative::kth(k)` (спуск по степеням двойки на итеративном дереве)
* **Связь:** k-я статистика — B.7, E.5; спуск — битовые приёмы (IV.C)

## **5. Динамическое дерево отрезков (по указателям, без сжатия)**
* **Определение:** диапазон координат `[0, N)` задан заранее, но сжатия нет: вершины создаются по требованию только на путях запросов/обновлений; отсутствующая вершина означает «нейтральный узел»
* **Идея:** корень покрывает весь `[0, N)`; спуск создаёт детей только при попадании в них; запрос по пустому поддереву — сразу нейтральный ответ
* **Почему работает:** каждый спуск создаёт O(log N) вершин; суммарно вершин — O(число операций · log N) — независимо от N
* **Сложность:** операция O(log N), память O(операции · log N); координатное сжатие не нужно — мост в VII
* **Обобщение:** с ленивыми операциями — механика D.6 на динамических вершинах (интервальные обновления на огромных координатах); персистентность — D.11
* **Реализация:** `SegmentTreeDynamic` (пул вершин `{l, r}` — индексы детей, `0` — пусто; `update(pos, x)`, `query(l, r)`)
* **Связь:** создание по требованию — D.11 (персистентность) и VII; разреженность — B.6

## **5.1. Сжатое по координатам дерево отрезков (coordinate compression)**
* **Определение:** статический аналог D.5: координаты операций известны заранее и сжимаются (сортировка уникальных + `lower_bound`) — дерево отрезков строится над сжатыми индексами, а не над всем универсумом
* **Идея:** пусть операции обращаются к `m` уникальным координатам из диапазона `[0, U)`; после сжатия обычное дерево на массиве (D.1) размера `m` отвечает за те же координаты; точки между координатами не хранятся
* **Почему работает:** любая операция маппится на сжатый индекс точно; память и глубина дерева зависят от `m`, а не от `U`
* **Сложность:** сжатие O(m log m), операция O(log m), память O(m) — против O(U) без сжатия
* **Границы:** только известные заранее координаты (появление новых — D.5 динамический, D.11 персистентный); сжатие переставляет индексы — при запросах границ `l, r` маппятся `lower_bound`'ами
* **Реализация:** `SegmentTreeCompressed` (сжатие координат + `SegmentTreeArray`-механика, `update`, `query`)
* **Связь:** динамическое дерево — D.5; сжатие — тот же приём, что C.6 и Sparse Table; k-я статистика по сжатым значениям — E.5

## **6. Lazy Propagation: Add on segment, sum on segment**
* **Определение:** отложенное прибавление: узел хранит «отложенный» сдвиг `lazy` — операцию, применённую к узлу целиком, но не переданную детям; при спуске — `push` передаёт lazy детям и обнуляет
* **Идея:** обновление отрезка покрывается O(log n) узлами — в каждом применяем сдвиг целиком за O(1) и кладём в lazy; дети пересчитываются только когда понадобятся (спуск)
* **Почему работает:** отсрочка корректна, потому что агрегат узла пересчитан сразу, а дети «догонят» при спуске; число проталкиваний — O(log n) на операцию
* **Сложность:** `add(l, r, x)`/`sum(l, r)` — O(log n)
* **Реализация:** `LazySegTreeAdd` (`tree[]`, `lazy[]`; `push`, рекурсивные `add_segment`, `query`)
* **Связь:** ленивость — мотив фибоначчиевой кучи (IV.B.2): платить за работу при извлечении, а не при вставке

## **7. Lazy Propagation: Assign on segment**
* **Определение:** присваивание значения на отрезке: узел хранит «флаг set + значение»; при `push` дети перезаписываются, их lazy заменяется на новое присваивание
* **Почему работает:** присваивание не коммутирует со старым lazy: старый сдвиг теряется при перезаписи — lazy-set заменяется, а не складывается
* **Сложность:** `assign(l, r, x)`/`sum(l, r)` — O(log n)
* **Обобщение:** комбинация add + set — D.8; присваивание — частный случай «функций над отрезком»
* **Реализация:** `LazySegTreeAssign` (lazy — «пусто / set(x)»; `push` перезаписывает детей)
* **Связь:** композиция операций — D.8; перезапись приоритетнее сложения

## **8. Lazy Propagation: Add and Assign combination**
* **Определение:** два вида отложенных операций: `add` и `set`; приоритет — `set` перекрывает `add` (при `set` на узел старый lazy сбрасывается; при `add` на узел с `set` — add накладывается на set)
* **Почему работает:** композиция: `set(v)` после `set(u)` — `set(v)`; `add(x)` после `set(v)` — `set(v + x)`; `add(x)` после `add(y)` — `add(x + y)` — узлы пересчитываются по правилам комбинации
* **Сложность:** `add`/`assign`/запрос — O(log n)
* **Обобщение:** «история операций» — мост в VII (персистентность: версии = снапшоты состояний); аффинные функции — та же композиция, что D.10
* **Реализация:** `LazySegTreeAddAssign` (`lazy_add`, `lazy_set` с флагом; `push` применяет set, затем add)
* **Связь:** комбинированные обновления — D.6/D.7; мост персистентности — VII, III.A.7

## **9. Массовые операции: параметризация нейтрального элемента и свёртки**
* **Определение:** одно дерево на любой запрос: операция свёртки `op` и нейтральный элемент `neut` — параметры (sum/min/max/gcd); `query` сводит ответы канонических узлов через `op`, начиная с `neut`
* **Почему работает:** достаточно ассоциативности: канонические узлы непересекаемы — порядок свёртки не важен; нейтральный элемент — «пустой ответ» пустого поддерева
* **Сложность:** те же O(log n) на операцию
* **Обобщение:** параметризация — мотив C.3 (Sparse Table Generic), IV.A.3 (компаратор); операции без обратимости (min/max/gcd) — в отличие от Fenwick (B.1), дерево отрезков не требует обратимости
* **Реализация:** `SegmentTreeGeneric` (`op` — `std::function<int(int,int)>`, `neut`; `update(i, x)`, `query(l, r)`)
* **Связь:** моноид и агрегаты — III.A.4; «неидемпотентные без обратимости» — D.1, C.5

## **10. Segment Tree Beats**
* **Определение:** операции, «улучшающие» отрезок массово: `min=` (chmin: `a[i] = min(a[i], x)`), `max=` (chmax), `%=` (по модулю), возведение в степень на отрезке, побитовые `&=`, `|=`, `^=`
* **Идея:** узел хранит экстремумы с кратностями: `max1`, `max2`, `cnt_max` (и зеркально `min1`, `min2`, `cnt_min`); для chmin: если `x ≥ max1` — ничего; если `max2 < x < max1` — пересчёт за O(1) (только максимумы: `sum −= cnt_max·(max1 − x)`); иначе — спуск; chmax — зеркально через минимумы
* **Почему работает (амортизация):** «частичное» применение возможно, когда затронуты только экстремумы — такие спуски либо увеличивают `max2`, либо уменьшают число «разных» значений в узле; потенциальная функция ограничена — амортизированно O(log n) на операцию (для min= + сумма)
* **Обобщение:** `%=`: если `max < x` — выход (ничего не меняется), иначе спуск — каждый элемент при делении уменьшается минимум вдвое, суммарно O(log max) делений на элемент; возведение в степень на отрезке: спуск при показателе > 1, значение быстро «взрывается» — с насыщением; побитовые: `&=` — если `(OR узла & x) == OR узла` — выход, если `(AND узла & x) == AND узла` — применяется ко всем за O(1), иначе спуск (для `|=` — зеркально через AND/OR; для `^=` — только если все биты в узле одинаковы)
* **Сложность:** chmin/chmax — O(log n) амортизированно (с поддержкой суммы); `%=`, степень, битовые — амортизированные оценки через тот же потенциал
* **Реализация:** `SegmentTreeBeats` (chmin, chmax, add, `sum`/`max`; «%=» и битовые — обобщения той же схемы, описанные выше)
* **Связь:** «второй экстремум» — потенциал, как в фибоначчиевой куче (IV.B.2); ленивость — D.6

## **11. Персистентное дерево отрезков (PST)**
* **Определение:** версии дерева: операция обновления создаёт новые узлы только на пути от корня к листу, остальные поддеревья переиспользуются; корень каждой версии — «снапшот» состояния
* **Идея:** пул вершин: каждый узел — `{left, right, sum}` (индексы в пуле); `update(prev_root, pos, x)` — клонирует узлы пути, меняя один; `query(root, l, r)` — по версии
* **Почему работает:** меняется O(log n) узлов на версию — новая версия стоит O(log n) памяти, не копируя всё дерево; старые версии остаются корректными (узлы неизменяемы)
* **Сложность:** обновление O(log n), запрос O(log n); память O(n + q·log n)
* **Применение:** k-я статистика на подмассиве (версии — префиксы по значениям), «история» операций — мост в VII
* **Обобщение:** персистентность — мотив III.A.7 (PersistentDSU) и VII; динамическое создание — D.5
* **Реализация:** `PersistentSegmentTree` (пул узлов; `update(prev, pos, x)` → новая версия, `query(root, l, r)`)
* **Связь:** неизменяемость узлов — мост в VII; снапшоты — III.A.6 (RollbackDSU)

## **12. 2D Segment Tree (дерево деревьев)**
* **Определение:** внешнее дерево по оси x; в каждом его узле — внутреннее дерево по оси y (полные, как в B.4, но деревья отрезков): обновление точки — путь по x, в каждой вершине — обновление по y; запрос прямоугольника — канонические x-узлы × y-запросы
* **Почему работает:** вложенность деревьев отрезков: прямоугольник разбивается на O(log n) x-полос, каждая — на O(log n) y-отрезков
* **Сложность:** построение O(n·m) (память O(n·m)), обновление/запрос O(log² n)
* **Границы:** память O(n·m) — при больших полях разреженные варианты (B.6, D.5)
* **Реализация:** `SegmentTree2D` (дерево деревьев на массивах; `update(x, y, v)`, `query(x1, y1, x2, y2)`)
* **Связь:** дерево деревьев — B.4, B.6, E.1; прямоугольники — A.2, C.4

# **E. ПРОДВИНУТЫЕ ДЕРЕВЬЯ**

## **1. Range Tree**
* **Определение:** дерево поиска по первому измерению, в каждой вершине — структура по второму (и так далее, до k измерений); запрос k-мерного прямоугольника — O(log^k n) узлов + размер ответа
* **Идея:** построение статического 2D: дерево по x (как дерево отрезков), в узле — отсортированный массив y-координат точек поддерева (слияние детей, как E.5); запрос — канонические x-узлы, в каждом — бинарный поиск по y
* **Почему работает:** вложенность структур: каждый уровень отсекает одно измерение; каноническое покрытие по x (O(log n) узлов) и бинарный поиск по y в каждом — O(log² n) на запрос подсчёта
* **Сложность:** построение O(n log n), запрос подсчёта в прямоугольнике O(log² n); k измерений — O(log^k n)
* **Реализация:** `RangeTree2D` (дерево по x со sorted массивами по y; `count(x1, x2, y1, y2)`)
* **Связь:** вложенность — B.4, D.12; sorted массивы в узлах — E.5; k измерений — обобщение до O(log^k n)

## **2. Interval Tree**
* **Определение:** дерево по координатам с центрами: в узле с центром `c` хранятся все интервалы, содержащие `c`, — отсортированные по левому и по правому краю; точечный запрос (stabbing) — спуск от корня, в каждом узле — бинарный поиск по покрывающим
* **Идея:** каждый интервал живёт ровно в одном узле дерева (в том, где он содержит центр); запрос точки `p` спускается по дереву, в узлах с `c ≥ p` берёт интервалы с `l ≤ p` (по правому краю отсекаются r ≥ p), с `c < p` — с `r ≥ p`
* **Почему работает:** путь запроса — O(log n) узлов, в каждом — один бинарный поиск; интервалы, содержащие `p`, ровно те, что лежат на пути с подходящим краем
* **Сложность:** построение O(n log n), запрос O(log n + k) (k — число найденных интервалов); динамические интервалы — версия с балансировкой (постановка: та же схема с BST-узлами)
* **Реализация:** `IntervalTree` (статический: узлы `{c, l_sorted, r_sorted, left, right}`; `query(p)` — список/число покрывающих)
* **Связь:** интервалы — задачи планирования и покрытия (`technique.md`); центр узла — тот же приём, что середина в D.6–D.8

## **3. Segment Tree with Fractional Cascading**
* **Определение:** ускорение спуска по дереву отрезков с отсортированными массивами (E.5): каждый узел хранит отсортированный массив значений и «переходы» `to` — для каждого элемента позиции того же элемента в детях; бинарный поиск выполняется один раз в корне, дальше — константные переходы по каскаду
* **Идея:** при спуске позиция `x` в узле даёт позиции в детях за O(1) через массив переходов (с поправкой на соседние элементы): каждый уровень — O(1), вместо бинарного поиска в каждом узле
* **Почему работает:** склеивание массивов: элементы детей входят в массив родителя — позиция в родителе определяет позицию в ребёнке с точностью до константы (проверка двух соседей); суммарно O(log n) переходов
* **Сложность:** построение O(n log n), запрос диапазона O(log n + ответов) (было O(log² n) в E.5); память O(n log n)
* **Реализация:** `FractionalCascading` (дерево со sorted массивами и `to`-переходами; `count_le(l, r, x)` — сколько элементов ≤ x на подотрезке)
* **Связь:** Merge Sort Tree — E.5 (та же задача без ускорения); «переходы по уровням» — мотив C.5 (Disjoint ST) и LCA

## **4. Li Chao Tree**
* **Определение:** динамическое дерево отрезков по x-координатам, в узле — прямая, «лучшая» в середине отрезка узла; вставка прямой — спуск с обменами по знаку на границах; запрос в точке — максимум прямых на пути
* **Идея:** вставка `line` в узел с текущей `cur`: в середине узла сравниваются значения; если новая лучше — обмен; затем спуск в ту половину, где старая может быть лучше (та, где знак сравнения на границе другой)
* **Почему работает:** две прямые пересекаются один раз — после точки пересечения одна всегда лучше: каждая пара «встречается» на одном пути — глубина дерева O(log C) ограничивает работу
* **Сложность:** вставка/запрос O(log C) (C — диапазон x); память O(число прямых · log C) — динамическое создание узлов (D.5)
* **Обобщение:** максимум/минимум — параметр (обёртка со знаком); прямые — частный случай выпуклых функций — CHT-оптимизация ДП (`dynamic.md`)
* **Реализация:** `LiChaoTree` (`{k, b}`-прямые, диапазон x параметром; `insert`, `query_max(x)`)
* **Связь:** CHT — `dynamic.md`; динамическое дерево — D.5; выпуклость — анализ

## **5. Merge Sort Tree**
* **Определение:** дерево отрезков, узел хранит отсортированный массив своего отрезка (построение — слияние массивов детей); запросы: «сколько элементов ≤ x на [l, r)» — канонические узлы + бинарный поиск; k-я статистика на подмассиве — спуск по значениям
* **Идея:** `count_le(l, r, x)` — по каноническим узлам суммы `upper_bound`-ов; `kth(l, r, k)` — бинарный поиск значения v с проверкой `count_le(l, r, v) ≥ k`
* **Почему работает:** отсортированные массивы — тот же мотив, что Range Tree (E.1): каноническое покрытие отрезка + бинарный поиск в каждом узле
* **Сложность:** построение O(n log n), `count_le` O(log² n), `kth` O(log C · log² n) (бинарный поиск по значению); память O(n log n)
* **Обобщение:** ускорение запросов до O(log n) — Fractional Cascading (E.3); статические подмассивы — k-я статистика без обновлений
* **Реализация:** `MergeSortTree` (sorted массивы в узлах; `count_le`, `kth`)
* **Связь:** k-я статистика — B.7, II.G.2; sorted массивы — E.1; ускорение — E.3

**VIII. КОНКУРЕНТНЫЕ (ПАРАЛЛЕЛЬНЫЕ) СТРУКТУРЫ**

> **Архитектура:** `ConcurrentStructures` (h.cpp) — класс ветки struct, наследует `PersistentStructures` (g.cpp). Вводит структуры для многопоточного доступа: lock-based (A), lock-free (B), wait-free (C), конкурентные контейнеры (D), специальные примитивы (E). > **Связи:** случайность и вероятностные структуры — `hashing.md` IV; офлайн и детерминизм — `technique.md`; амортизация — `analysis.md`; lock-free Skip List — `hashing.md` IV; конкурентные версии персистентных списков — VII.

# **Основные понятия и принципы**

* **Что это:** структуры, допускающие одновременный доступ нескольких потоков: блокирующие (локи — взаимное исключение), неблокирующие (атомарные операции, CAS-циклы — прогресс без локов), wait-free (гарантированное конечное число шагов); плюс специальные примитивы — seqlock, RCU, lock-free Skip List
* **Почему выделяется в отдельный класс:** локи дешёвы в написании, но дороги в работе (контенция, блокировки, инверсия приоритетов); lock-free структуры обходят это атомикой, но платят сложностью доказательства; задачи — высоконагруженные очереди, счётчики, кэши, базы данных
* **Ключевые принципы:** прогресс: блокирующий — поток ждёт лок; lock-free — система прогрессирует (хотя бы один поток делает шаг); wait-free — каждый поток делает конечное число шагов (B.1, C); атомарность: CAS/load/store + порядки памяти acquire/release/seq_cst (B.4); инварианты точек: пустая очередь — фиктивный узел (B.2), монотонные счётчики — нет ABA (B.3); ABA-проблема — теги, hazard pointers, epoch (B.5); читатели без локов — seqlock (E.1), RCU (E.2)
* **Как распознать:** «много потоков пишут/читают» — мутекс-структуры (A) или lock-free при строгих требованиях (B); «очередь без блокировок» — Michael-Scott (B.2); «один продюсер, один потребитель» — wait-free SPSC (C); «часто читаем, редко пишем» — seqlock/RCU (E); «упорядоченное множество под нагрузкой» — lock-free Skip List (E.3)
* **Границы:** лок-free гарантирует прогресс системы, но не отдельных потоков (звездоголодание возможно); wait-free — редкий класс, обычно SPSC или ограниченные структуры; блокирующие структуры страдают от контенции и блокировок; CAS-циклы деградируют при высокой контенции (спин); память lock-free — безопасное освобождение (B.5, E.2)

# **A. LOCK-BASED СТРУКТУРЫ**

## **1. Mutex-protected Queue/Stack**
* **Определение:** контейнер + `std::mutex`: каждая операция захватывает лок, работает, отпускает; push/pop — O(1)
* **Идея:** взаимное исключение — критические секции сериализуются; инвариант контейнера соблюдается между лочами
* **Почему работает:** лок гарантирует исключительный доступ; сложность — только в области действия лоча (чем короче, тем меньше контенция)
* **Сложность:** O(1) амортизированно; блокировка — цена контенции
* **Обобщение:** std::lock_guard (RAII); несколько мьютексов — D (сегментные/бакетные локи)
* **Реализация:** `MutexQueue` (mutex + deque), `MutexStack` (mutex + vector)
* **Связь:** блокирующие vs неблокирующие — A.4; конкурентные контейнеры — D

## **2. Reader-Writer Lock**
* **Определение:** разделяемый доступ: много читателей одновременно, писатель — один; read_lock/read_unlock/write_lock/write_unlock
* **Идея:** читатели не конфликтуют друг с другом — общий лок; писатель ждёт всех читателей; классика — mutex + два condition_variable (или `std::shared_mutex`)
* **Почему работает:** инвариант «либо один писатель, либо много читателей»; приоритет писателя — защита от голодания
* **Сложность:** читатели O(1) при отсутствии писателей; писатель — O(1) ожидания завершения
* **Обобщение:** приоритеты (писатели-преимущественный); `std::shared_mutex` (C++17) — готовая реализация
* **Реализация:** `RWLock` (mutex + две condition_variable; писатели приоритетнее)
* **Связь:** condition variable — A.3; сериализация — A.1

## **3. Condition Variable очереди**
* **Определение:** блокирующая очередь: pop ждёт, пока очередь непуста; push уведомляет — `condition_variable::notify_one`
* **Идея:** pop: уникальный лок + while (empty) wait; push: лок + push + notify — wait отпускает лок и блокирует
* **Почему работает:** condition_variable атомарно отпускает лок и засыпает; потерянные пробуждения исключаются проверкой в цикле (спуриусные пробуждения)
* **Сложность:** O(1) амортизированно; блокирующий pop — ждёт данных
* **Обобщение:** таймауты, закрытие очереди (notify_all), приоритетные очереди
* **Реализация:** `ConditionQueue` (mutex + condition_variable + deque; блокирующие push/pop)
* **Связь:** RWLock — A.2 (два cv); системные очереди — мост в системное программирование

## **4. Спинлоки (backoff) и блокирующие vs неблокирующие примитивы**
* **Определение:** спинлок — активное ожидание (цикл чтения флага) вместо сна; backoff — экспоненциальная пауза между попытками; сравнение: спин хорош при коротких критических секциях, лок — при длинных
* **Идея:** `std::atomic_flag` + test_and_set; при неудаче — `std::this_thread::yield()` или пауза; backoff снижает контенцию кэша (коалесценция)
* **Почему работает:** при короткой секции ожидание дешевле переключения контекста; backoff разводит попытки потоков по времени
* **Сложность:** O(1) на успех; в худшем случае — спин до освобождения
* **Обобщение:** блокирующий vs неблокирующий прогресс — вся ось B; гибрид (спин → сон)
* **Реализация:** `SpinLock` (atomic_flag + backoff)
* **Связь:** прогресс и гарантии — B; атомика — B.4

# **B. LOCK-FREE СТРУКТУРЫ**

## **1. Lock-free Stack (Treiber)**
* **Определение:** стек на атомарном указателе вершины: push — новый узел, CAS(top, old, new); pop — CAS(top, old, old->next); цикл до успеха
* **Идея:** push/pop — единственная критическая точка (top); CAS-цикл повторяет попытку при чужом изменении — структура не блокируется, прогресс гарантирован (кто-то обязательно успеет)
* **Почему работает:** инвариант «top — начало списка»; CAS линеаризуется в момент успеха; конкурирующие потоки не застревают (lock-free: хотя бы один делает шаг)
* **Сложность:** O(1) ожидаемо на операцию; контенция — повторные CAS
* **Обобщение:** ABA-проблема (B.5); память — hazard pointers/epoch (E.2); wait-free варианты — C
* **Реализация:** `TreiberStack` (atomic<Node*> top, CAS-циклы)
* **Связь:** атомика и порядки — B.4; ABA — B.5

## **2. Lock-free Queue (Michael-Scott)**
* **Определение:** очередь на двух атомарных указателях (head — фиктивный узел, tail) + CAS-циклы; enqueue — CAS на tail, dequeue — CAS на head
* **Идея:** фиктивный узел — «точка отсчёта»: head всегда указывает на удалённый узел, tail — на последний; enqueue: запись данных, CAS(tail, old, new); dequeue: CAS(head, old, old->next)
* **Почему работает:** пустая очередь корректна (head == tail == фиктивный узел); CAS-инварианты удерживают связность списка при гонках
* **Сложность:** O(1) ожидаемо на операцию; контенция на head/tail
* **Обобщение:** приоритетные очереди; блокирующие pop (sleep при пустоте); dequeue возвращает null при пустой
* **Реализация:** `MichaelScottQueue` (два atomic<Node*>, фиктивный узел)
* **Связь:** Treiber Stack — B.1; спин/пауза — A.4

## **3. Lock-free Deque**
* **Определение:** двусторонняя очередь с атомарными концами: head/tail — монотонные счётчики, слоты — кольцевой массив; push/pop с любого конца — CAS на своём счётчике
* **Идея:** монотонные счётчики не «переиспользуются» — нет ABA на индексах; слот читается с acquire, пишется с release; полная/пустая — по разности счётчиков (возврат false — ограниченная семантика)
* **Почему работает:** счётчики уникальны на всё время жизни — гонки индексов невозможны; каждая операция — конечное число атомарных шагов
* **Сложность:** O(1) на операцию; ограниченный размер (емкость параметром); неограниченный — существенно сложнее (анализ в md)
* **Обобщение:** неограниченный lock-free deque — сложные алгоритмы (ссылка в md); вытеснение задач — work-stealing deque (Chase-Lev), основа планировщиков (мост в системное программирование)
* **Реализация:** `LockFreeDeque` (кольцо атомарных слотов, head/tail — atomic счётчики, capacity параметром)
* **Связь:** кольцевые буферы — I; wait-free SPSC — C.1

## **4. Atomic операции и memory ordering**
* **Определение:** load/store/fetch_add/compare_exchange на `std::atomic`; порядки памяти: relaxed (только атомарность), acquire (чтение-блокировка после), release (запись-блокировка до), seq_cst (глобальный порядок); CAS-циклы — идиома «прочитай-проверь-запиши»
* **Идея:** release-запись + acquire-чтение той же ячейки образует «синхронизацию»: всё, что записано до release, видно после acquire; seq_cst — единая точка порядка
* **Почему работает:** формальная модель памяти (happens-before); relaxed годится для счётчиков без зависимостей; acquire/release — для передачи данных; seq_cst — для инвариантов порядка
* **Сложность:** O(1); seq_cst дороже relaxed (барьеры)
* **Обобщение:** CAS-циклы (счётчики, стеки B.1); fetch_add — wait-free счётчик
* **Реализация:** демо: `AtomicCounter` (fetch_add и CAS-цикл), передача флага с acquire/release
* **Связь:** модель памяти — `analysis.md`; вся секция B

## **5. ABA-проблема и её решения**
* **Определение:** CAS(top, A, B) может успешно выполниться, хотя A — «старый» узел, возвращённый в кучу и переиспользованный (его next уже изменён); классика — Treiber pop
* **Идея:** сравнение только указателя не отличает «тот же адрес» от «тот же узел в том же состоянии»
* **Почему работает:** решения: tagged pointer (младшие биты — счётчик, меняется при каждом CAS), hazard pointers (список защищённых указателей), epoch-based reclamation (E.2) — откладывают освобождение
* **Сложность:** тег — O(1), требует выравнивания; hazard pointers — O(число потоков) памяти
* **Обобщение:** тегированный указатель в uintptr_t — общий приём; RCU (E.2) — reclamation вместо защиты
* **Реализация:** `TaggedTreiberStack` (указатель + тег в одном атомарном слове)
* **Связь:** Treiber — B.1; RCU/epoch — E.2

# **C. WAIT-FREE СТРУКТУРЫ**

## **1. Wait-free Queue (SPSC)**
* **Определение:** очередь «один продюсер — один потребитель»: кольцо + атомарные head/tail; push — запись слота + fetch_add(tail); pop — чтение + fetch_add(head); каждый поток владеет своим концом — нет CAS-циклов, шагов конечное число
* **Идея:** разделение владения: продюсер пишет только tail-слоты, потребитель — только head; каждая операция — фиксированное число атомарных шагов → wait-free
* **Почему работает:** гонка только на одной ячейке (tail видит head, head видит tail); release/acquire передают данные; переполнение — проверка до записи (возврат false)
* **Сложность:** O(1) на операцию — строго; память — фиксированная (кольцо)
* **Обобщение:** wait-free MPSC/MPMC — существенно сложнее; кольцо как примитив — мост в системное программирование
* **Реализация:** `SPSCWaitFreeQueue` (кольцо атомарных слотов, head/tail — fetch_add)
* **Связь:** LockFreeDeque — B.3 (монотонные счётчики); wait-free — определение в B

## **2. Wait-free Stack (SPSC, ограниченный, массив + seq)**
* **Определение:** стек «один продюсер — один потребитель» на массиве: атомарный счётчик top (размер) + слоты с монотонными готовностями seq; push — fetch_add(1) и запись слота; pop — чтение вершины ДО декремента с CAS-подтверждением позиции
* **Идея:** продюсер пишет только свободные позиции (≥ top), занятые не трогает — чтение не гоняется с записью; готовность слота — seq[p] = 2k−1 (k-я запись позиции): потребитель ждёт значения своего k-го чтения и НЕ сбрасывает seq (нет потери готовности); CAS(top, t, t−1) — освобождается ровно прочитанная позиция, при конкуренции с push — повтор
* **Почему работает:** записи и чтения позиции чередуются (LIFO): k-я запись позиции читается её k-м pop; seq монотонен — потребитель всегда дождётся своего значения; CAS-подтверждение исключает освобождение не той позиции
* **Сложность:** push — O(1) (fetch_add, wait-free); pop — O(1) с возможным повтором при конкуренции с push; каждая попытка — конечное число шагов
* **Обобщение:** строго wait-free SPSC-стек (без повторов) — сложнее; по-настоящему wait-free и проще — очередь (C.1), где концы разведены по потокам
* **Реализация:** `SPSCWaitFreeStack` (массив слотов + seq; локальные счётчики записей/чтений у продюсера и потребителя)
* **Связь:** wait-free очередь — C.1; SPSC-разделение — системное программирование

# **D. CONCURRENT CONTAINERS**

## **1. Concurrent Vector (сегменты)**
* **Определение:** вектор с сегментными локами: блоки размера B, каждый со своим мьютексом; чтение стабильного сегмента — без лока (сегмент неизменяем после заполнения); рост — новый сегмент под локом роста
* **Идея:** сегменты-«страницы»: разные потоки работают с разными сегментами параллельно; граница сегмента — точка синхронизации
* **Почему работает:** сегмент заполняется один раз (одним писателем-владельцем), дальше — read-only; таблица сегментов растёт редко (глобальный лок)
* **Сложность:** push_back — O(1) амортизированно; чтение — O(1) без блокировок на стабильных сегментах
* **Обобщение:** refcount-сегменты; сегментные схемы — мотив VI (блоки)
* **Реализация:** `ConcurrentVector` (сегменты + mutex на сегмент и на рост)
* **Связь:** блоки и хвосты — VI.A; lock-based — A.1

## **2. Concurrent HashMap (бакетные локи)**
* **Определение:** хеш-таблица с цепочками и локом на бакет: insert/find/erase — захват лока только своего бакета; разный хеш — параллельно
* **Идея:** разблокировка по хешу: контенция ограничена бакетом; resize — глобальный лок (редко)
* **Почему работает:** инвариант цепочки соблюдается в пределах бакета; число бакетов — параметр (контенция/память)
* **Сложность:** O(1) ожидаемо на операцию; resize — O(число ключей)
* **Обобщение:** lock-free хеш-таблицы (сложнее); разделяемые бакеты
* **Реализация:** `ConcurrentHashMap` (vector<mutex> по бакетам + цепочки)
* **Связь:** хеширование — `hashing.md`; бакеты — VI

## **3. concurrent_queue / concurrent_stack**
* **Определение:** типовые обёртки: `MutexQueue` (A.1), `MutexStack` (A.1), `ConditionQueue` (A.3) — готовые конкурентные контейнеры; выбор по семантике блокировки
* **Идея:** единый интерфейс push/pop/try_pop — замена контейнера без смены кода
* **Почему работает:** инкапсуляция синхронизации в контейнере
* **Сложность:** как базовая структура
* **Обобщение:** конкурентные версии других контейнеров — D.1, D.2
* **Реализация:** мост к A.1–A.3
* **Связь:** lock-based — A

# **E. СПЕЦИАЛЬНЫЕ ПРИМИТИВЫ**

## **1. Seqlock (write-lock + версия)**
* **Определение:** счётчик версий + флаг писателя: читатель — два чтения версии вокруг данных, повтор при нечётной версии или изменении; писатель — версия++ , запись, версия++
* **Идея:** читатели не блокируются и не пишут — только читают версию (spin при писателе); нечётная версия = «идёт запись»
* **Почему работает:** инвариант «версия меняется только парно»; повтор чтения при гонке гарантирует согласованность (retry loop — но не блокировка)
* **Сложность:** читатель — O(1) с возможным повтором; писатель — O(1) (жёстко: один писатель)
* **Обобщение:** несколько писателей — не seqlock (нужен лок); данные — массив/структура копированием
* **Реализация:** `Seqlock` (atomic версия + данные; `write(idx, x)`, `write_pair(a, b)` — пара полей в одном разделе, `read(idx)`, `snapshot(out)` — согласованный снимок, число полей — параметр конструктора)
* **Связь:** RWLock — A.2 (блокирующий аналог); RCU — E.2

## **2. RCU (Read-Copy-Update)**
* **Определение:** читатели — без блокировок (загрузка указателя); писатель — копия, правка, атомарная замена указателя; освобождение старой копии — после «благодатного периода» (epoch), когда все читатели завершили критические секции
* **Идея:** чтение — одна атомарная загрузка; запись — copy + swap; память — отложенное освобождение (grace period), читатели регистрируются счётчиком
* **Почему работает:** читатели видят либо старую, либо новую версию (acquire/release); освобождение после всех читателей — безопасность (по сути hazard pointer для всех)
* **Сложность:** читатель — O(1); писатель — O(размер данных) копия; reclamation — O(ожидание читателей)
* **Обобщение:** reclamation для lock-free — мост к B.5 (epoch вместо hazard pointers); per-thread регистрация — масштабируемость
* **Реализация:** `RCUStore` (atomic указатель, счётчик активных читателей, отложенное освобождение)
* **Связь:** ABA — B.5; seqlock — E.1 (оба — читатели без блокировок)

## **3. Lock-free Skip List (мост из hashing.md IV)**
* **Определение:** Skip List (hashing.md IV) с атомарными указателями уровней: вставка — CAS-цепочка снизу вверх (неудача уровня не ломает список — узел остаётся на нижних уровнях); поиск — чтение без блокировок
* **Идея:** уровни — «оптимизация»: отказ CAS на верхнем уровне оставляет узел в списке (уровень 0 обязателен) — простота против классики (Harris-маркировка для удаления)
* **Почему работает:** инвариант поиска — порядок уровня 0; верхние уровни только ускоряют; вставка линеаризуется в момент CAS уровня 0
* **Сложность:** поиск/вставка — O(log n) ожидаемо; удаление — сложно (маркировка) — анализ
* **Обобщение:** удаление с логической маркировкой (Harris) — анализ; конкурентные упорядоченные множества
* **Реализация:** `LockFreeSkipList` (insert/search без удаления; CAS снизу вверх; приоритеты — mt19937)
* **Связь:** Skip List — hashing.md IV; Treiber CAS-циклы — B.1; атомика — B.4

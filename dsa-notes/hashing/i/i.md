# **A. ДОКАЗУЕМАЯ БЕЗОПАСНОСТЬ**

## **1. Модель случайного оракула (Random Oracle Model)**

### **1.1. Определение**
* Хеш-функция `H` моделируется как **случайная функция**: для каждого нового запроса `x` возвращает случайное `y ∈ {0,1}^m`
* **Допущение:** ни один алгоритм не может «предсказать» `H(x)` без вычисления

### **1.2. Преимущества**
* Упрощает доказательства безопасности (достаточно показать, что атака требует `Ω(2^{m/2})` запросов)
* Многие криптографические протоколы доказуемо безопасны в модели ROM

### **1.3. Ограничения**
* Реальные хеш-функции — **детерминированные** (не случайные)
* Существуют атаки, которые работают в реальности, но не в ROM
* Конструкции, безопасные в ROM, могут быть небезопасны в реальности

## **2. Standard Model Security**

### **2.1. Определение**
* Доказательства безопасности **без допущений** о случайном оракуле
* Основываются только на свойствах примитивов (сторгость,并与困难ые предположения)

### **2.2.困难ые предположения**
* **Collision Resistance:** сложно найти `x ≠ y` с `H(x) = H(y)`
* **Second Preimage Resistance:** по `x` сложно найти `x' ≠ x` с `H(x') = H(x)`
* **Preimage Resistance:** по `y` сложно найти `x` с `H(x) = y`

## **3. Game-based Proofs**

### **3.1. Идея**
* Безопасность определяется как **невозможность выигрыша** в игре между adhesive и verifier
* **Игра:** adhesive делает запросы → verifier отвечает → adhesive пытается «выиграть» (найти коллизию, предсказать хеш)

### **3.2. Пример: HMAC**
* **Игра:** adhesive получает `HMAC(K, ·)` для произвольных входов
* **Цель:** вычислить `HMAC(K, x)` для нового `x`
* **Доказательство:** если HMAC insecure → PRF insecure →ollision-resistant хеш insecure

# **B. АВТОМАТИЗИРОВАННАЯ ВЕРИФИКАЦИЯ**

## **1. Формальные системы**

### **1.1. Coq**
* Интерактивный теорем-проевер (ITP)
* **Применение:** доказательство корректности алгоритмов, верификация криптографических протоколов
* **Пример:** верификация SHA-3 в Coq ( proven correct)

### **1.2. Isabelle/HOL**
* Автоматический теорем-проевер с поддержкой SMT
* **Применение:** формальная верификация хеш-таблиц, проверка инвариантов

## **2. Model Checking**

### **2.1. Определение**
* Проверка: выполняется ли_temporal property для всех возможных состояний системы
* **Модель:** конечный автомат (states × transitions)
* **Свойства:** LTL (Linear Temporal Logic) — `□(safe)`, `◇(goal)`

### **2.2. Применение к хеш-таблицам**
* Проверка: нет deadlock, все операции завершаются, инвариант `count ≤ size` сохраняется

## **3. Symbolic Execution**

### **3.1. Определение**
* Выполнение программы с **символическими** значениями входов
* На каждом условном переходе: ветвление на два пути (true/false)
* **Цель:** достижимость определённых состояний (ошибок, уязвимостей)

### **3.2. Применение**
* Поиск уязвимостей в реализациях хеш-функций
* Генерация тестов для покрытия всех ветвлений

# **C. СТАТИЧЕСКИЙ И ДИНАМИЧЕСКИЙ АНАЛИЗ**

## **1. Fuzzing**

### **1.1. Определение**
* Автоматическая генерация случайных/случайно-структурированных входов
* **Цель:** найти крэши, assertion failures, ошибки памяти

### **1.2. Типы**
* **Mutation-based:** изменение существующих входов (flip битов, вставка, удаление)
* **Generation-based:** генерация входов с нуля (на основе грамматики/формата)

## **2. Side-channel Analysis**

### **2.1. Типы**
* **Временна́я атака:** измерение времени выполнения → утечка информации
* **Энергетическая атака:** анализ энергопотребления (DPA, SPA)
* **Кэш-атака:** наблюдение за кэш-промахами → восстановление ключей

### **2.2. Защита**
* **Constant-time implementation:** время не зависит от входных данных
* Пример: `if (secret_bit)` → `result |= (secret_bit << i)` без ветвления

## **3. Differential Testing**

### **3.1. Идея**
* Сравнение двух реализаций одной хеш-функции
* Генерация одинаковых входов → проверка совпадения выходов
* **Различия:** potential bugs в одной из реализаций

### **3.2. Применение**
* Проверка корректности: OpenSSL vs_libreSSL vs_BoringSSL
* Обнаружение regression errors при обновлении библиотек
